# AI-First 强约束新式 PRD 管理器 v2.0 — Superpowers 融合版

## 🎯 核心目标

将传统 PRD 升级为**人与 AI 共同遵守的可执行契约**，融合两大方法论之长：

**来自 AIFirstPRDManager（设计层能力）**:
- ✅ **AI 可解析**：所有规则、流程、约束结构化，杜绝"凭感觉生成"
- ✅ **设计先行原则**：所有设计类阶段必须全部完成并确认后，才能进行任务分解
- ✅ **全链路可追溯**：从需求到代码全链路关联，一键定位问题根源
- ✅ **技术栈实时验证**：6 维度框架防止使用过时/废弃技术

**来自 Superpowers（执行层能力）**:
- ✅ **Subagent 并行执行**：状态内可并行派遣多个独立子代理加速
- ✅ **TDD 铁律**：无失败测试不写生产代码，红绿重构循环
- ✅ **双阶段审查**：规范合规审查 + 代码质量审查，每任务必审
- ✅ **系统化调试**：4 阶段根因分析，95% 首修成功率
- ✅ **证据优先文化**：无验证不声明完成，实测数据说话

## 🔄 工作流程（Pipeline + Inversion + Subagent + Reviewer 模式）

### ⚠️ 核心原则（必须遵守）

**Execute each phase in order. Do NOT skip any phase.**
**Do NOT proceed to next phase until current phase is confirmed by user.**
**All phases must have human confirmation gates.**
**设计先行原则：所有设计类阶段(0-6)必须全部完成并确认后，才能进入执行阶段(7-9)**
**每文档必审：每个阶段产出的文档必须经过审核才能进入下一环节**

**AI 操作**：

### Phase 1: 调研 → 可视化场景确认

**产出**：用例图、业务活动图

#### 🧠 Step 1.0: 编写前 — 头脑风暴（在约束中探索）

> 加载 `skills/brainstorming/SKILL.md` 执行苏格拉底式设计探索

**核心原则**（来自 brainstorming 技能）：
- 一次只问一个问题（禁止连珠炮）
- 给出 2-3 个方案供选择（而非开放式问题）
- YAGNI 原则：ruthlessly 剔除不需要的功能
- 增量验证：每步确认后再深入

**Anti-Pattern 警告**：
- ❌ "这太简单了不需要设计" → 每个项目都必须走完设计流程
- ❌ 直接给出最终方案 → 应先探索再收敛
- ❌ 忽略"不做"的边界 → 必须明确排除项

**头脑风暴检查清单**：
- [ ] 核心用户是谁？他们的技术水平如何？
- [ ] 主要使用场景？请描述 2-3 个典型场景
- [ ] 成功标准？有哪些关键指标？
- [ ] 有哪些异常情况或边界条件？
- [ ] "不做"的边界是什么？（明确排除项）
- [ ] 是否有类似系统的参考实现？

#### Step 1.1: 收集需求信息（Inversion 模式）

使用 Inversion 模式收集需求，结合 brainstorming 的苏格拉底技巧：

**Q1: 核心用户是谁？**
> 结合 brainstorming: 提供 2-3 个候选用户画像供选择

**Q2: 主要使用场景？**
> 结合 brainstorming: 每个场景追问"最坏情况是什么？"

**Q3: 成功标准？**
> 结合 brainstorming: 区分"必须有"和"最好有"

**Q4: 边界情况？**
> 结合 brainstorming: 极端值、空值、并发、超时等

#### Step 1.2-1.3: 生成用例图 + 业务活动图

（保持原有格式不变，详见优化版内容）

#### 🔍 Step 1.4: 编写后 — 文档审核

> 加载 `references/enhanced-review-protocol.md` 执行审核

**审核维度 — 需求文档专用**:

| 审核项 | 检查点 | 极端情况压力测试 |
|-------|--------|----------------|
| **场景完整性** | 主流程是否全覆盖？ | 零用户并发、海量数据、网络中断 |
| **边界清晰度** | "做/不做"是否明确？ | 灰色地带需求能否判定归属 |
| **参与者定义** | 角色是否完整？ | 未登录用户、过期会话、权限越界 |
| **异常覆盖** | 异常场景表是否充分？ | 所有外部依赖全部失败的级联场景 |
| **用例独立性** | 用例间是否有隐含耦合？ | 单独执行某用例是否会破坏其他 |
| **可追溯性** | 用例 ID 是否已生成？ | 每个用例是否能追溯到业务目标 |

**审核输出**:
```
需求文档审核报告:
✅ 通过项: {count} 项
⚠️ 需修改: {count} 项（附具体问题和建议）
❌ 阻塞项: {count} 项（必须修复后才可继续）
审核结论: PASS / CONDITIONAL_PASS / FAIL
```

**质量检查**：

- [ ] 所有主流程已覆盖
- [ ] 分支场景已识别
- [ ] 异常情况已处理
- [ ] 用例 ID 已生成
- [ ] 追溯记录已更新
- [ ] **🆕 文档审核已通过**

**门禁检查**：

```

1. 场景是否完整？有没有遗漏？
2. "不做"的边界是否清晰？
```

#### 🔍 Step 2.3: 编写后 — 文档审核

**审核维度 — 架构文档专用**:

| 审核项 | 检查点 | 极端情况压力测试 |
|-------|--------|----------------|
| **技术栈验证** | 是否通过 Phase 1.5 验证？ | 某技术突然 EOL 的替代方案 |
| **组件职责** | 是否单一职责？有无上帝组件？ | 单组件故障对整体的影响面 |

## ⚙️ 执行模式

### Mode A: 完整模式（Full Mode）— 推荐

- **描述**: 执行完整的 10 阶段流水线 + 每文档审核 + Subagent 并行
- **适用场景**: 新功能从零开始开发，中大型项目
- **特点**: 最高质量保证，完整审计轨迹

### Mode B: 快速模式（Fast Mode）

- **描述**: 保留 10 阶段顺序 + 每文档审核（简化），执行层使用 inline 替代 subagent
- **适用场景**: 小功能、原型开发、时间紧迫
- **注意**: 仍然遵循 10 阶段顺序和每文档审核，但简化部分产出

### Mode C: 审计模式（Audit Mode）

- **描述**: 仅审查现有 PRD/代码的合规性
- **适用场景**: 代码审查、质量检查、第三方交付评估

### Mode D: 修复模式（Fix Mode）

- **描述**: 从错误溯源开始，定位问题并修复
- **适用场景**: Bug 修复、问题排查
- **特点**: 自动路由到 systematic-debugging 或 error-diagnosis

## ✅ 质量门禁（v2.0 更新）

### 流程约束（必须 100% 遵守）

- [x] **禁止**跳过任何开发阶段，必须严格按照 10 个阶段顺序执行
- [x] **禁止**在未完成上一阶段人工确认前，进入下一阶段
- [x] **禁止**修改已经人工确认过的规范/图表，除非走正式的变更流程
- [x] **禁止**在没有生成对应图表/规范前，直接生成代码
- [x] **🆕 禁止**在任何文档编写后跳过审核环节
- [x] **🆕 禁止**在文档编写前跳过头脑风暴探索

### 技术约束

- [x] **禁止**擅自引入 `project-constraint.yaml` 中未列出的依赖库/框架
- [x] **禁止**修改项目的基础架构、目录结构，除非有明确授权
- [x] **禁止**跨层调用，必须遵循模块职责定义
- [x] **禁止**在代码中硬编码敏感信息，必须使用配置文件
- [x] **禁止**在未通过 Phase 1.5 技术栈验证的情况下进行架构设计
- [x] **禁止**使用已 EOL 或已废弃的技术
- [x] **🆕 禁止**无失败测试就写生产代码（TDD Iron Law）
- [x] **🆕 禁止**用 self-review 替代真实审查

### 行为约束

- [x] **禁止**臆造需求、臆造规则，所有实现必须严格匹配 PRD 中的规范
- [x] **禁止**删除、修改历史的追溯记录，所有变更必须留痕
- [x] **禁止**忽略校验清单中的检查项，完成任务后必须先自检
- [x] **🆕 禁止**在无验证证据的情况下声明任务完成
- [x] **🆕 禁止**在未通过 Code Review 的情况下合并代码
