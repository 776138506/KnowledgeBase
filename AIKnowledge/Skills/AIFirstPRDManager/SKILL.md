# AI-First 强约束新式 PRD 管理器 v2.0 — Superpowers 融合版

## 🎯 核心目标

将传统 PRD 升级为**人与 AI 共同遵守的可执行契约**，融合两大方法论之长：

**来自 AIFirstPRDManager（设计层能力）**:
- ✅ **AI 可解析**：所有规则、流程、约束结构化，杜绝"凭感觉生成"
- ✅ **设计先行原则**：所有设计类阶段必须全部完成并确认后，才能进行任务分解
- ✅ **全链路可追溯**：从需求到代码全链路关联，一键定位问题根源
- ✅ **技术栈实时验证**：6 维度框架防止使用过时/废弃技术

**来自 Superpowers（执行层能力）**:
- ✅ **Subagent 并行执行**：状态内可并行派遣多个独立子代理加速
- ✅ **TDD 铁律**：无失败测试不写生产代码，红绿重构循环
- ✅ **双阶段审查**：规范合规审查 + 代码质量审查，每任务必审
- ✅ **系统化调试**：4 阶段根因分析，95% 首修成功率
- ✅ **证据优先文化**：无验证不声明完成，实测数据说话

## 🔄 工作流程（Pipeline + Inversion + Subagent + Reviewer 模式）

### ⚠️ 核心原则（必须遵守）

**Execute each phase in order. Do NOT skip any phase.**
**Do NOT proceed to next phase until current phase is confirmed by user.**
**All phases must have human confirmation gates.**
**设计先行原则：所有设计类阶段(0-6)必须全部完成并确认后，才能进入执行阶段(7-9)**
**每文档必审：每个阶段产出的文档必须经过审核才能进入下一环节**

### Phase 1: 调研 → 可视化场景确认

**产出**：用例图、业务活动图

#### 🧠 Step 1.0: 编写前 — 头脑风暴（在约束中探索）

> 加载 `skills/brainstorming/SKILL.md` 执行苏格拉底式设计探索

**核心原则**（来自 brainstorming 技能）：
- 一次只问一个问题（禁止连珠炮）
- 给出 2-3 个方案供选择（而非开放式问题）
- YAGNI 原则：ruthlessly 剔除不需要的功能
- 增量验证：每步确认后再深入

**Anti-Pattern 警告**：
- ❌ "这太简单了不需要设计" → 每个项目都必须走完设计流程
- ❌ 直接给出最终方案 → 应先探索再收敛
- ❌ 忽略"不做"的边界 → 必须明确排除项

**头脑风暴检查清单**：
- [ ] 核心用户是谁？他们的技术水平如何？
- [ ] 主要使用场景？请描述 2-3 个典型场景
- [ ] 成功标准？有哪些关键指标？
- [ ] 有哪些异常情况或边界条件？
- [ ] "不做"的边界是什么？（明确排除项）
- [ ] 是否有类似系统的参考实现？

#### Step 1.1: 收集需求信息（Inversion 模式）

使用 Inversion 模式收集需求，结合 brainstorming 的苏格拉底技巧：

**Q1: 核心用户是谁？**
> 结合 brainstorming: 提供 2-3 个候选用户画像供选择

**Q2: 主要使用场景？**
> 结合 brainstorming: 每个场景追问"最坏情况是什么？"

**Q3: 成功标准？**
> 结合 brainstorming: 区分"必须有"和"最好有"

**Q4: 边界情况？**
> 结合 brainstorming: 极端值、空值、并发、超时等

#### Step 1.2-1.3: 生成用例图 + 业务活动图

#### 🔍 Step 1.4: 编写后 — 文档审核

> 加载 `references/enhanced-review-protocol.md` 执行审核

**审核维度 — 需求文档专用**:

| 审核项 | 检查点 | 极端情况压力测试 |
|-------|--------|----------------|
| **场景完整性** | 主流程是否全覆盖？ | 零用户并发、海量数据、网络中断 |
| **边界清晰度** | "做/不做"是否明确？ | 灰色地带需求能否判定归属 |
| **参与者定义** | 角色是否完整？ | 未登录用户、过期会话、权限越界 |
| **异常覆盖** | 异常场景表是否充分？ | 所有外部依赖全部失败的级联场景 |
| **用例独立性** | 用例间是否有隐含耦合？ | 单独执行某用例是否会破坏其他 |
| **可追溯性** | 用例 ID 是否已生成？ | 每个用例是否能追溯到业务目标 |

**审核输出**:
```
需求文档审核报告:
✅ 通过项: {count} 项
⚠️ 需修改: {count} 项（附具体问题和建议）
❌ 阻塞项: {count} 项（必须修复后才可继续）
审核结论: PASS / CONDITIONAL_PASS / FAIL
```

**质量检查**：

- [ ] 所有主流程已覆盖
- [ ] 分支场景已识别
- [ ] 异常情况已处理
- [ ] 用例 ID 已生成
- [ ] 追溯记录已更新
- [ ] **🆕 文档审核已通过**

### Phase 1.3: 原型设计 → 需求可视化 🆕

**产出**：线框图、高保真原型、可交互原型、UI 设计规范

**目标**：将 Phase 1 的抽象用例转化为可视化原型，早期验证用户流程和交互设计

#### 🧠 Step 1.3.0: 编写前 — 头脑风暴（原型规划）

> 加载 `skills/prototype-design/SKILL.md` 执行原型设计规划

**核心问题**：

1. **原型目标**：
   - 验证用户流程？
   - 展示视觉效果？
   - 用户测试？
   - 利益相关者演示？

2. **保真度选择**：
   - **低保真（线框图）**：快速探索布局，适合早期
   - **中保真**：加入基础样式，适合流程验证
   - **高保真**：完整视觉效果，适合最终确认

3. **工具选择**：
   - **Figma/墨刀**：适合协作、评论、用户测试
   - **HTML/CSS**：适合可交互原型、代码复用
   - **混合模式**：Figma 设计 + HTML 实现关键流程

4. **覆盖范围**：
   - 核心流程（必须）
   - 异常流程（建议）
   - 边界场景（可选）

**输出**：原型设计计划书

#### 🛡️ Step 5.0.5: 编写中 — 测试神圣性原则（预防式）

> **测试用例一旦写好，就成为规范的守护者。编写测试时必须确保每个断言都有明确的规范来源。**
> **详见 `references/constraint-checklist.md` BC-004.5**

**每写一个测试用例时自检**：

```
□ 这个测试场景来自 Phase 1 的哪个用例？(UC-ID)
□ 这个测试断言来自 Phase 4 的哪条规则？(R-ID) 或哪个 Gherkin 场景？
□ 如果这个测试失败了，我能确定是"实现错了"还是"测试写错了"吗？
  → 如果不能确定 → 测试的预期值/断言不够明确，需要更精确
□ 测试是否独立？（不依赖执行顺序、不依赖其他测试的状态）
□ 测试名称是否清晰描述了业务意图而非技术细节？
```

**测试用例的三级权威链（不可违反）**：

```
Phase 1 需求文档 / Phase 4 规范定义
  ↓ (测试必须忠实反映)
Phase 5 测试用例矩阵
  ↓ (实现必须满足)
Phase 7 实现代码

如果 测试失败:
  ↓
  测试符合规范? → YES → 实现是错的 → 修改实现
                    NO  → 测试本身有 bug → 可改测试但必须留痕说明原因
```

#### 📐 Step 7.0.5: 编写中 — 全量编码原则自检（预防式，每行代码都遵循）

> **⚠️ 这是整个流程中最关键的原则检查点。每写一个函数/类/文件，立即执行以下自检。**
> **不是写完代码后再检查，是写的过程中就遵循。能一次做对就不要反复改。**

**【写每个函数之前问自己】**:

**SRP**:
- □ 这个函数只做一件事吗？名字是否包含 "and"？
- □ 函数体是否 ≤ 20 行？（超长 → 拆分）
- □ 圈复杂度是否 ≤ 10？（if/else/for/while/case 嵌套过深 → 拆分）

**DIP**:
- □ import 的是接口还是具体类？（必须导入接口/抽象类）
- □ 是否通过构造函数注入依赖？禁止在函数内部 `new` 具体类

**LoD**:
- □ 是否有 `a.getB().getC()` 链式调用？（→ 违反 LoD，应该只和直接朋友对话）

**KISS**:
- □ 这段代码是否有更简单的实现方式？
- □ 是否引入了不必要的抽象层？

**DRY**:
- □ 这段逻辑是否在其他地方已存在？（Ctrl+F 搜索一下再决定是否新建）
- □ 如果在复制粘贴代码 → 立即停止，提取为共享函数

**YAGNI**:
- □ 这个参数/方法/类是当前任务需要的，还是我觉得"以后可能有用"？
- □ 如果不需要 → 删掉，不要预留

**组合 > 继承**:
- □ 我用继承是因为真的是 "is-a"，还是为了复用代码？
- □ 继承层次是否超过 3 层？

**LSP**（如果涉及继承/多态）:
- □ 子类是否加强了前置条件或弱化了后置条件？
- □ 是否用了 instanceof 做类型判断后走不同逻辑？

**BC-006: WHY > WHAT**:
- □ 这个函数/类的注释说明了为什么这样做，而不是做了什么吗？
- □ commit message 包含根因分析了吗？

**【TDD 循环中的原则检查】**:

```
RED 阶段（写测试）:
  ├── 测试名称是否清晰描述业务意图？（非技术细节）
  ├── 测试是否只验证一个行为？（SRP）
  └── 🛡️ 测试断言是否精确？能否仅凭此断言判定"实现对/错"？（BC-004.5）

GREEN 阶段（写实现）:
  ├── 只写了让测试通过的最小代码？（YAGNI）
  ├── 没有添加测试不要求的功能？（BC-001 不臆造需求）
  ├── 实现是否符合 Phase 4 的规范定义？
  └── 🛡️ 如果测试不通过 → **先判定测试是否正确反映规范**，再决定改实现还是改测试（BC-004.5）

REFACTOR 阶段（优化）:
  ├── 重构是否保持了测试全绿？（安全网）
  ├── 重构是否提升了可读性而非增加抽象？（KISS）
  ├── 是否消除了重复代码？（DRY）
  └── 🛡️ 重构后如有测试失败 → **绝对禁止修改测试来适配重构**。如果规范未变则实现破坏了契约 → 回滚重构或修复实现
```

## ⚙️ 执行模式

### Mode A: 完整模式（Full Mode）— 推荐

- **描述**: 执行完整的 10 阶段流水线 + 每文档审核 + Subagent 并行
- **适用场景**: 新功能从零开始开发，中大型项目
- **特点**: 最高质量保证，完整审计轨迹

### Mode B: 快速模式（Fast Mode）

- **描述**: 保留 10 阶段顺序 + 每文档审核（简化），执行层使用 inline 替代 subagent
- **适用场景**: 小功能、原型开发、时间紧迫
- **注意**: 仍然遵循 10 阶段顺序和每文档审核，但简化部分产出

### Mode C: 审计模式（Audit Mode）

- **描述**: 仅审查现有 PRD/代码的合规性
- **适用场景**: 代码审查、质量检查、第三方交付评估

### Mode D: 修复模式（Fix Mode）

- **描述**: 从错误溯源开始，定位问题并修复
- **适用场景**: Bug 修复、问题排查
- **特点**: 自动路由到 systematic-debugging 或 error-diagnosis
