# 全链路可追溯体系

> 从需求到代码的全链路关联，一键定位问题根源
> 
> **版本**: 1.0.0  
**用途**: 错误溯源、影响分析、变更追踪

---

## 🎯 核心目标

建立完整的**唯一 ID 追溯链**，实现：

- ✅ **需求溯源**：从代码追溯到原始需求
- ✅ **错误定位**：快速找到问题的根本原因
- ✅ **影响分析**：评估变更的影响范围
- ✅ **知识沉淀**：将经验转化为约束

## 🆔 ID 命名规范

```
[类型前缀]-[3位序号]
```

### 类型前缀列表

| 前缀 | 类型 | 示例 | 说明 |
|------|------|------|------|

| **API** | 接口 | API-001 | API Endpoint |

| **CHG** | 变更 | CHG-001 | Change Request |

## 🔗 追溯链结构

### 标准追溯关系

```
UC-[001] (用例)
    ↓ 生成
C-[001] (组件)
    ↓ 分解为
T-[001], T-[002] (任务)
    ↓ 实现
API-[001] (接口)
    ↓ 包含
R-[001], R-[002] (规则)
    ↓ 映射到
S-[001], S-[002] (场景)
    ↓ 验证
TEST-[001], TEST-[002] (测试)
    ↓ 对应
CODE-[001] (代码提交)
```

## 🔍 错误溯源操作流程

当线上或测试出现 Bug 时，按以下步骤操作：

### Step 1: 复现 Bug

```markdown
## Bug 报告

**Bug ID**: BUG-[001]
**发现时间**: YYYY-MM-DD HH:MM
**发现环境**: 生产/测试/开发
**严重程度**: P0/P1/P2/P3

### 复现步骤

1. [操作步骤 1]
2. [操作步骤 2]
3. [操作步骤 3]

### 预期结果
[描述预期行为]

### 实际结果
[描述实际行为]

### 截图/日志
[附上截图或关键日志]
```

### Step 2: 锁定出错位置

根据 Bug 类型，锁定对应的追溯 ID：

| Bug 类型 | 锁定目标 | 查找方法 |
|---------|---------|---------|
| **逻辑错误** | CODE-XXX | Git blame 定位代码行，找到对应的 CODE-ID |
| **接口异常** | API-XXX | 根据请求路径找到对应的接口定义 |
| **数据错误** | DB-XXX / F-XXX | 根据报错字段找到对应的数据表和字段 |
| **规则违反** | R-XXX | 根据业务规则找到对应的规则定义 |
| **场景遗漏** | UC-XXX / S-XXX | 根据缺失的场景找到对应的用例或 Gherkin 场景 |

### Step 3: 向上追溯

通过 `trace.md` 向上追溯，找到根因：

```
示例：用户注册时邮箱校验不生效

Step 1: 锁定代码位置
→ CODE-015: commit abc1234 "实现邮箱校验"

Step 2: 向上追溯
→ TEST-008: "邮箱格式校验测试" ← 关联
→ R-003: "邮箱格式校验规则" ← 关联
→ API-001: "POST /api/users/register" ← 关联
→ T-001: "实现注册接口" ← 关联
→ C-001: "UserService" ← 关联
→ UC-001: "用户邮箱注册" ← 根因！

Step 3: 分析根因
→ 查看 UC-001 的定义：
   发现需求中明确要求"支持 + 号邮箱"
   
→ 查看 R-003 的定义：
   发现规则只验证 @ 符号，未处理 + 号
   
→ 结论：**规则定义遗漏**（不是代码 bug）
```

### Step 4: 分类根因类型

| 根因类型 | 占比 | 典型表现 | 解决方案 |
|---------|------|---------|---------|
| **需求理解错** | 30% | 功能与 PRD 不一致 | 回到 Phase 1 修正用例 |
| **规则定义错** | 25% | 规则模糊或有遗漏 | 回到 Phase 5 补充规则 |
| **设计缺陷** | 20% | 架构不合理 | 回到 Phase 2/4 修改设计 |
| **编码错误** | 20% | 逻辑 bug | 直接修复代码 |
| **流程跳步** | 5% | 缺少必要的图表/设计 | 补充缺失的产出物 |

### Step 5: 修复并更新追溯链

**修复流程**:

1. **修复问题**
   ```bash
   # 根据根因类型选择修复方案
   if 根因是"规则定义错":
       # 1. 更新 rules 文件
       # 2. 更新相关图表
       # 3. 重跑受影响的测试
   ```

2. **更新追溯记录**
   ```markdown
   ## 变更记录
   
   | 变更 ID | 类型 | 时间 | 影响 | 说明 |
   |---------|------|------|------|------|
   | CHG-[XXX] | 规则修正 | now | R-003, TEST-008 | 补充 + 号邮箱支持 |
   ```

3. **同步到全局追溯表**
   - 更新 `trace-total.md`
   - 更新功能级 `trace.md`
   - 记录新的 CODE-ID

4. **补充错误案例库**
   ```markdown
   # resources/error_cases.md
   
   ## EC-[XXX]: 邮箱校验遗漏 + 号
   
   **发生时间**: YYYY-MM-DD
   **功能**: 用户注册
   **根因**: 规则定义遗漏
   **现象**: user+test@example.com 无法注册
   **修复方案**: 补充 RFC 5322 邮箱格式校验
   **预防措施**: 所有邮箱相关规则必须引用 RFC 5322
   ```

## 📊 影响分析

### 变更影响评估

当需要修改某个产出物时，使用追溯链评估影响：

```markdown
## 变更影响评估

### 变更请求

| 属性 | 值 |
|-----|---|
| 变更 ID | CHG-[XXX] |
| 变更类型 | 修改/新增/删除 |
| 变更对象 | R-003: 邮箱格式校验规则 |
| 变更原因 | [原因] |
| 申请人 | [姓名] |
| 时间 | YYYY-MM-DD |

### 影响范围分析

**向下影响**（子节点）:
- R-003 → S-003 (邮箱格式场景), S-004 (无效邮箱场景)
- S-003 → TEST-008 (正常邮箱测试), TEST-009 (特殊字符测试)
- TEST-008 → CODE-015 (校验函数代码)

**向上影响**（父节点）:
- R-003 → API-001 (注册接口)
- API-001 → T-001 (注册任务) → C-001 (UserService) → UC-001 (用户注册用例)

### 影响统计

| 影响层级 | 影响数量 | 需要更新的文件 |
|---------|---------|-------------|
| 规则层 | 1 | 08-business-rules.md |
| 场景层 | 2 | 09-gherkin.md |
| 测试层 | 2 | test_user_register.py |
| 代码层 | 1 | user_service.py |
| 文档层 | 1 | trace.md |
| **总计** | **7** | **7 个文件** |

### 风险评估

| 风险项 | 等级 | 缓解措施 |
|-------|------|---------|
| 回归风险 | 中 | 必须重跑所有关联测试 |
| 性能风险 | 低 | 新增的校验逻辑简单 |
| 兼容性风险 | 低 | 新增对现有数据无影响 |

### 决策建议

□ **批准变更** - 影响可控，可以执行
□ **有条件批准** - 需要额外测试
□ **拒绝变更** - 影响过大，需要替代方案
```

### Git Hook 自动追踪

```bash
# .git/hooks/commit-msg

#!/bin/bash
# 自动在提交信息中添加 CODE-ID

COMMIT_MSG_FILE=$1
COMMIT_MSG=$(cat "$COMMIT_MSG_FILE")

# 检查是否已有 CODE-ID
if ! echo "$COMMIT_MSG" | grep -q "CODE-"; then
    # 自动生成新的 CODE-ID
    CODE_ID=$(python scripts/generate_trace_id.py CODE)
    
    # 在提交信息开头添加 CODE-ID
    echo "$CODE_ID: $COMMIT_MSG" > "$COMMIT_MSG_FILE"
fi
```

## 📈 追溯覆盖率指标

### 定义

| 指标 | 公式 | 目标值 |
|-----|------|--------|
| **追溯完整率** | 有追溯 ID 的节点数 / 总节点数 | 100% |
| **追溯连通率** | 有父子关系的节点数 / 总节点数 | ≥95% |
| **追溯准确率** | 正确关联的节点数 / 总关联数 | ≥98% |
| **变更响应率** | 变更后 24h 内更新追溯的比例 | 100% |
