# 头脑风暴协议（Brainstorming Protocol）

> **版本**: 1.0.0
> **所属**: AIFirstPRDManager v2.0 融合版
> **用途**: 定义每个阶段文档编写前的头脑风暴流程、技巧和约束探索方法
> **核心来源**: Superpowers brainstorming 技能 + AIFirstPRDManager 约束体系

---

## 1. 核心理念

```
┌─────────────────────────────────────────────────────────────┐
│                  头脑风暴协议核心思想                          │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│   传统方式: 拿到需求 → 直接开始写文档                         │
│                                                             │
│   增强方式:                                                  │
│     🧠 编写前: 在约束中系统化探索                             │

│   为什么需要编写前头脑风暴?                                   │

│   "多花10分钟在前面探索，少花10小时在后面返工"                │

```

## 2. 协议总览

### 2.1 双触发时机

头脑风暴在**两个时机**被触发：

```
时机 A: 文档编写前（Pre-Writing Brainstorming）
  目的: 探索设计空间，识别盲区，明确边界
  输出: 设计决策记录 + 风险清单 + 约束确认
  
时机 B: 文档评审中（In-Review Brainstorming）
  目的: 验证极端情况，挑战假设，发现隐藏缺陷
  输出: 极端场景清单 + 脆弱点报告 + 改进建议
```

### 2.2 与审核协议的关系

```
增强审核协议 (enhanced-review-protocol)
  │
  ├── 编写前: ──────────→ 本协议 (Pre-Writing)
  │     头脑风暴            在约束中探索
  │
  ├── 编写中:              (正常产出)
  │     按规范编写
  │
  └── 编写后: ──────────→ 审核协议 (Post-Writing)
        结构化审核            多维度检查
        +                     +
        极端压力测试 ←───────── 本协议 (In-Review)
                              验证极端情况
```

## 3. Pre-Writing 头脑风暴（编写前）

### 3.1 苏格拉底式提问框架

来自 `skills/brainstorming/SKILL.md` 的核心技巧：

#### 黄金规则

| 规则 | 说明 | 违规示例 |
|------|------|---------|
| **一次一问** | 每次只问一个问题 | ❌ 连珠炮式提问 |
| **给选项** | 提供 2-3 个候选方案 | ❌ 开放式"你想要什么？" |
| **YAGNI** | ruthlessly 剔除不需要的功能 | ❌ "万一以后需要呢？" |
| **增量验证** | 每步确认后再深入 | ❌ 一步到位给出完整方案 |
| **明确排除** | 必须定义"不做"的边界 | ❌ 只说"做什么" |

#### 提问模板库

**通用问题（适用于所有阶段）**：

```markdown
## 通用头脑风暴问题集

### Q1: 核心用户与场景
- 这个功能/模块的核心用户是谁？
- 他们的技术水平如何？（新手/专家/混合）
- 最典型的使用场景是什么？请描述 2-3 个
- 最坏情况下的使用场景是什么？

### Q2: 成功标准
- 怎么算"做完了"？可量化的指标？
- 有哪些"必须有"(Must Have) vs "最好有"(Nice to Have)？
- 如果只能实现 80%，哪些功能最先砍？

### Q3: 边界与排除
- 这个功能的边界在哪里？
- 明确不做(Out of Scope)的是什么？为什么？
- 有没有灰色地带的需求？如何判定归属？

### Q4: 约束与限制
- project-constraint.yaml 中有哪些相关约束？
- 有没有历史错误案例需要避免？
- 技术/时间/资源上有什么硬性限制？
```

**分阶段专用问题**：

#### Phase 1 专用（需求探索）

```markdown
## Phase 1: 需求头脑风暴

### 用户画像探索
- 提供候选画像:
  A. {画像A描述}
  B. {画像B描述}
  C. {画像C描述}
- 问: 主要服务哪类用户？是否有遗漏？

### 场景深度挖掘
对每个主场景追问:
  - 正常路径是什么？
  - 最常见的异常路径是什么？
  - 最罕见的但必须处理的异常是什么？
  - 如果这个场景完全失败了，降级方案是什么？

### 反向思考
- 如果这个功能不存在，用户会怎样？
- 有没有更简单的方式达到同样目的？
- 这个功能是否可以拆成多个小功能分期交付？
```

#### Phase 2 专用（架构探索）

```markdown
## Phase 2: 架构头脑风暴

### 技术选型验证
- 当前技术栈能否支撑所有已识别的场景？
- Phase 1.5 验证结果中有没有"需关注"的技术？
- 是否存在技术债务需要在架构层面解决？

### 组件分解探索
- 候选分解方案:
  A. {按业务领域分解}
  B. {按技术层次分解}
  C. {按数据流向分解}
- 各方案的优劣对比？

### 非功能性需求
- 性能目标: P50/P95/P99 延迟要求？
- 可用性目标: 几个 9？容灾策略？
- 安全要求: 认证/授权/加密/审计？
- 扩展预期: 6个月/1年/3年的规模预估？
```

#### Phase 3 专用（接口/数据探索）

```markdown
## Phase 3: 模块设计头脑风暴

### API 设计探索
- RESTful vs GraphQL vs gRPC？为什么？
- 版本控制策略: URL versioning / Header / 无版本？
- 分页/排序/过滤的统一规范？
- 错误响应格式: RFC 7807 / 自定义？

### 数据模型探索
- 第三范式 vs 故意反范式？具体哪里反范式？为什么？
- 索引策略: 覆盖哪些查询模式？
- 数据生命周期: 归档/删除/软删？
- 数据一致性: 强一致 vs 最终一致？各用于什么场景？
```

#### Phase 4 专用（规范探索）

```markdown
## Phase 4: 规范定义头脑风暴

### 状态机探索
- 列出所有你能想到的状态（包括中间态）
- 列出所有你能想到的状态转换（包括非法转换）
- 有没有"悬空"状态？（能进入但不能离开的状态）
- 并发操作时状态如何处理？

### 规则完备性探索
- 所有业务规则都能用表格表达吗？
- 规则之间的优先级如何确定？
- 规则冲突时的裁决机制？
- 边界值的精确行为: ±0, ±ε, 最大值+1, 最小值-1?
```

#### Phase 5 专用（测试探索）

```markdown
## Phase 5: 测试设计头脑风暴

### 覆盖盲区探测
- Happy Path 都覆盖了吗？
- Error Path 有没有遗漏？
- 边界值: 0, 1, -1, MAX, MAX+1, NULL, 空, 超长?
- 并发场景: 同一资源同时读写？
- 时序依赖: 操作顺序颠倒会怎样？

### 测试数据策略
- 测试数据从哪来？Mock / Fixture / Seed？
- 测试间数据隔离怎么做？
- 敏感数据的测试处理？
```

#### Phase 6 专用（任务分解探索）

```markdown
## Phase 6: 任务分解头脑风暴

### 粒度验证
- 每个任务能在 2 小时内完成吗？
- 每个任务的验收标准客观吗？（能自动判断通过/失败）
- 任务之间有循环依赖吗？
- 关键路径上的任务如果延迟 50% 会怎样？
```

### 3.2 头脑风暴执行流程

```
Step 1: 加载约束环境
  ├── 加载 project-constraint.yaml
  ├── 加载 constraint-checklist.md
  ├── 加载前一阶段的产出物（作为输入）
  └── 加载历史 error_cases.md（如有）

Step 2: 运行通用问题集
  └── 完成 4 个通用维度的探索

Step 3: 运行当前阶段专用问题集
  └── 完成分阶段问题的深入探索

Step 4: 记录设计决策
  ├── 决策: 最终选择了什么方案
  ├── 候选: 考虑过但未选择的方案及原因
  ├── 风险: 识别出的潜在风险
  └── 约束: 确认或新增的约束条件

Step 5: 用户确认
  └── 展示决策记录，获得确认后进入文档编写
```

## 4. In-Review 头脑风暴（评审中）

### 4.1 目的与定位

当文档编写完成后进行审核时，除了结构化检查外，还需要用**攻击者思维**挑战文档：

```
普通审核: "这个文档写得对不对？"
In-Review 头脑风暴: "这个文档在什么情况下会出错？"
```

### 4.2 攻击者思维框架

#### 4.2.1 五维攻击矩阵

| 攻击维度 | 攻击手法 | 典型问题 |
|---------|---------|---------|
| **🔥 数据破坏** | 注入极端数据 | 超长、Unicode、NULL注入、特殊字符 |
| **⚡ 并发攻击** | 制造竞态条件 | 同时写入、读-写冲突、分布式不一致 |
| **⏰ 时间扭曲** | 利用时间边缘 | 闰秒、时钟回拨、时区跨越、过期Token |
| **🔗 依赖斩断** | 外部依赖失效 | 单点故障、级联超时、毒药消息 |
| **🔓 权限越界** | 绕过访问控制 | 水平越权、垂直越权、IDOR |

#### 4.2.2 攻击剧本生成器

```markdown
## In-Review 头脑风暴 — 攻击剧本

### 剧本 1: 数据破坏攻击
**目标**: {文档中的某个接口/功能}
**攻击向量**: 
  1. 发送超长字符串 (10MB+) → 是否有长度校验？
  2. 发送 Unicode 特殊字符 (🦄↺ℵ) → 编码是否正确处理？
  3. 发送 NULL/undefined → 是否有空值保护？
  4. 发送嵌套 JSON (10000层) → 是否有深度限制？
**防御检查**: 文档中是否定义了对应防护措施？

### 剧本 2: 并发竞态攻击
**目标**: {涉及状态变更的功能}
**攻击向量**:
  1. 同一用户并发提交两次相同请求 → 幂等性保证？
  2. 两个用户同时修改同一资源 → 乐观锁/悲观锁？
  3. 读-写-读不一致 → 事务隔离级别？
**防御检查**: ...

... (每个关键功能至少一个攻击剧本)
```

### 4.3 极端场景生成方法

#### 方法 1: 边界值分析法扩展

```
标准边界值: [min, min+, typical, max-, max]
扩展边界值: [NULL, empty, min-1, min, min+, 0, 1, max-, max, max+1, overflow]
特殊值: NaN, Infinity, -Infinity, undefined, 负零, 非数字字符串
编码陷阱: BOM头, 不同换行符(CR/LF/CRLF), 全角/半角混排
```

#### 方法 2: 故障模式推导

```
对于每个组件/接口:
  1. 它依赖什么外部资源？（DB/Cache/API/文件系统）
  2. 每个依赖可能怎么失败？（超时/拒绝/返回错误/返回脏数据）
  3. 失败传播路径是什么？（级联影响面）
  4. 当前设计中有对应的降级/熔断/重试机制吗？
```

#### 方法 3: 历史案例回溯

```
参考 resources/error_cases.md 中的历史错误:
  - 类似项目中出过什么问题？
  - 当前设计中是否已有针对性预防？
  - 如果没有，是否需要在当前阶段补充？
```

### 4.4 In-Review 输出模板

```markdown
## In-Review 头脑风暴报告 — {文档名}

### 攻击概览
- **测试文档**: {filename}
- **攻击面数量**: {n} 个关键功能点
- **生成攻击剧本**: {n} 个
- **发现脆弱点**: {n} 个

### 脆弱点详情

| # | 脆弱点 | 所在位置 | 攻击类型 | 严重度 | 文档中是否有防护 | 建议 |
|---|--------|---------|---------|--------|-----------------|------|
| V1 | ... | 行XX | 数据/并发/时间/依赖/安全 | Critical/High/Med/Low | ✅有/❌无 | ... |

### 攻击剧本摘要
（附完整攻击剧本，每个包含: 目标、向量、防御检查）

### 结论
- 🟢 健壮: 所有攻击都有对应防护
- 🟡 可接受: 少数低风险点可在后续迭代补充
- 🔴 存在风险: {n} 个高严重度脆弱点需立即修复 → 可能阻塞
```

## 5. 头脑风暴质量保障

### 5.1 Anti-Pattern 黑名单

| Anti-Pattern | 问题 | 正确做法 |
|-------------|------|---------|
| "这太简单不需要头脑风暴" | 简单≠无风险 | 即使简单功能也要走流程（可能更快完成） |
| 直接给出最终方案 | 排除更好选择 | 先探索 2-3 个选项再收敛 |
| 跳过"不做"的讨论 | 范围必然膨胀 | 明确 Out-of-Scope 并记录理由 |
| 一次性回答所有问题 | 信息过载导致遗漏 | 一次一问，逐步深入 |
| 用"应该没问题"代替验证 | 主观臆测 | 用证据和极端场景验证 |

### 5.2 质量检查清单

**Pre-Writing 质检**：
- [ ] 已加载所有约束文件
- [ ] 通用问题集已完成（4个维度）
- [ ] 专用问题集已完成（当前阶段）
- [ ] 设计决策已记录（含候选方案和原因）
- [ ] 风险清单已识别
- [ ] 用户已确认设计决策

**In-Review 质检**：
- [ ] 对每个关键功能生成了至少 1 个攻击剧本
- [ ] 五维攻击矩阵已覆盖
- [ ] 脆弱点已分级（Critical/High/Med/Low）
- [ ] 每个脆弱点都有对应建议
- [ ] 结论明确（🟢/🟡/🔴）

### 5.3 时间预算指南

| 阶段 | Pre-Writing 建议时长 | In-Review 建议时长 |
|------|--------------------|--------------------|
| Phase 1 (需求) | 15-20 分钟 | 10-15 分钟 |
| Phase 2 (架构) | 20-30 分钟 | 15-20 分钟 |
| Phase 3 (模块) | 15-20 分钟 | 10-15 分钟 |
| Phase 4 (规范) | 15-20 分钟 | 10-15 分钟 |
| Phase 5 (测试) | 10-15 分钟 | 15-20 分钟 |
| Phase 6 (任务) | 10-15 分钟 | 5-10 分钟 |

> 注: 这是 AI Agent 的"思考时间"，不是用户等待时间。Agent 应在内部完成探索后再呈现结果。

## 6. 工具集成

### 6.1 与 brainstorming 技能的关系

本协议是 `skills/brainstorming/SKILL.md` 的**结构化和扩展版本**：

```
brainstorming/SKILL.md (Superpowers 原版)
  ├── 苏格拉底提问技巧 ←── 直接采用
  ├── 9步设计流程 ←── 直接采用
  ├── YAGNI 原则 ←── 直接采用
  └── Visual Companion ←── 可选工具

brainstorming-protocol.md (本协议 — 扩展版)
  ├── 继承上述全部内容
  ├── + 分阶段专用问题模板库
  ├── + Pre-Writing / In-Review 双触发机制
  ├── + 设计决策记录模板
  ├── + 攻击者思维框架 (In-Review)
  ├── + 五维攻击矩阵
  ├── + 质量检查清单
  └── + 时间预算指南
```

### 6.2 与约束体系的关系

```
project-constraint.yaml (全局约束)
  ↑ 被头脑风暴读取和引用
  ↓ 可能被头脑风暴产生的新约束更新

constraint-checklist.md (铁律)
  ↑ 作为头脑风暴的红线边界
  ↓ 头脑风暴不能违反任何铁律

error_cases.md (历史错误)
  ↑ 作为头脑风暴的风险参考
  ↓ 头脑风暴产生的风险可能成为新的 error case
```
