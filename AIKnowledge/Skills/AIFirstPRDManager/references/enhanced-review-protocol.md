# 增强审核协议（Enhanced Review Protocol）

> **版本**: 1.0.0
> **所属**: AIFirstPRDManager v2.0 融合版
> **用途**: 定义每个阶段文档编写后的审核标准、流程和极端情况压力测试方法

---

## 1. 核心理念

```
┌─────────────────────────────────────────────────────────────┐
│                  增强审核协议核心思想                          │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│   传统审核: "看起来没问题" → 通过                              │
│                                                             │
│   增强审核:                                                  │
│     🧠 编写前: 头脑风暴（在约束中探索边界）                     │
│     📝 编写后: 结构化审核（多维度检查清单）                     │
│     🔥 压力测试: 极端情况验证（正常路径之外的破坏性测试）        │
│     🔗 追溯: 每条意见都可追溯到具体检查项                      │
│                                                               │
│   核心原则:                                                  │
│   - 不信任"直觉"，只相信证据                                  │
│   - 不放过模糊表述，必须精确化                                 │
│   - 不假设"正常情况"，必须验证极端                             │
│   - 不跳过任何阶段，每文档必审                                 │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

## 2. 审核流程总览

### 2.1 三段式审核

每个阶段的文档产出都必须经过**三段式审核**：

```
                    ┌──────────────────┐
                    │   文档编写前      │
                    │  🧠 头脑风暴      │
                    │  (brainstorming)  │
                    └────────┬─────────┘
                             │ 探索完成，开始编写
                             ▼
                    ┌──────────────────┐
                    │   文档编写中      │
                    │  📝 按规范产出    │
                    └────────┬─────────┘
                             │ 初稿完成
                             ▼
                    ┌──────────────────┐
                    │   文档编写后      │
                    │  🔍 结构化审核    │
                    │  + 极端压力测试   │
                    └────────┬─────────┘
                             │
                    ┌────────┴─────────┐
                    │                  │
                    ▼                  ▼
              ╔═══════════╗     ╔═══════════╗
              ║  PASS ✅  ║     ║  FAIL ❌  ║
              ╚════╤═════╝     ╚════╤═════╝
                    │                  │
                    ▼                  ▼
             进入下一阶段         修改后重新审核
```

### 2.2 审核角色

| 角色 | 职责 | 来源 |
|------|------|------|
| **头脑风暴者** | 在约束中探索设计空间，识别盲区 | brainstorming 技能 |
| **结构化审核员** | 按检查清单逐项审查文档质量 | 本协议 |
| **压力测试员** | 设计极端场景挑战文档的鲁棒性 | 本协议 |
| **决策者** | 根据审核结果决定 PASS/FAIL/CONDITIONAL | 用户 (Human) |

## 3. 分阶段审核标准

### 3.1 Phase 1: 需求文档审核

#### 审核维度表

| # | 维度 | 权重 | 检查点 | 极端压力测试 |
|---|------|------|--------|-------------|
| 1.1 | 场景完整性 | ⭐⭐⭐⭐⭐ | 主流程是否全覆盖？ | 零用户并发、海量数据、网络全中断 |
| 1.2 | 边界清晰度 | ⭐⭐⭐⭐⭐ | "做/不做"是否明确？ | 灰色地带需求能否判定归属 |
| 1.3 | 参与者定义 | ⭐⭐⭐ | 角色是否完整？ | 未登录、过期会话、权限越界 |
| 1.4 | 异常覆盖 | ⭐⭐⭐⭐ | 异常场景表充分？ | 所有外部依赖全部失败的级联 |
| 1.5 | 用例独立性 | ⭐⭐⭐ | 用例间无隐含耦合？ | 单独执行某用例破坏其他 |
| 1.6 | 可追溯性 | ⭐⭐⭐⭐ | 用例 ID 已生成？ | 每个用例→业务目标映射完整 |

#### 审核脚本模板

```markdown
## 需求文档审核报告

### 基本信息
- **文档**: {文件名}
- **审核时间**: {timestamp}
- **审核人**: {agent_id}

### 逐项检查

#### 1.1 场景完整性 [权重: ⭐⭐⭐⭐⭐]
- [ ] 所有主流程(Primary Flows)已识别并描述
- [ ] 每个主流程有对应的成功/失败出口
- [ ] 预期(Prescribed)和禁止(Prohibited)行为明确区分
- **压力测试**: 
  - 场景A在零并发下是否合理？
  - 场景B在10x数据量下是否仍有效？
  - 全网络中断时的降级策略？
- **结论**: ✅ PASS / ⚠️ CONDITIONAL / ❌ FAIL
- **备注**: {具体发现}

#### 1.2 边界清晰度 [权重: ⭐⭐⭐⭐⭐]
- [ ] In-Scope 明确列出
- [ ] Out-of-Scope 明确列出（含理由）
- [ ] Future/Follow-up 与当前版本的界限清晰
- **压力测试**: 
  - 给出一个灰色地带需求 → 能否立即判定？
  - 需求范围变更的影响面评估？
- **结论**: ✅ PASS / ⚠️ CONDITIONAL / ❌ FAIL

... (其余维度同上格式)

### 汇总统计
- ✅ 通过: {n} 项
- ⚠️ 需修改: {n} 项 (非阻塞)
- ❌ 阻塞: {n} 项 (必须修复)

### 最终判定
**审核结论**: PASS / CONDITIONAL_PASS / FAIL

### 阻塞项详情（如有）
| # | 阻塞项 | 位置 | 建议 |
|---|--------|------|------|
| 1 | ... | 行XX | ... |

### 修改建议（如有）
| # | 问题 | 严重度 | 具体建议 |
|---|------|--------|---------|
| 1 | ... | Critical/Important/Minor | ... |
```

### 3.2 Phase 2: 架构文档审核

| # | 维度 | 权重 | 检查点 | 极端压力测试 |
|---|------|------|--------|-------------|
| 2.1 | 技术栈验证 | ⭐⭐⭐⭐⭐ | 是否通过 Phase 1.5？ | 某技术突然 EOL 的替代方案 |
| 2.2 | 组件职责 | ⭐⭐⭐⭐ | 单一职责？无上帝组件？ | 单组件故障对整体影响面 |
| 2.3 | 依赖关系 | ⭐⭐⭐⭐ | 无循环依赖？ | 依赖链最深路径超时传播 |
| 2.4 | 安全性 | ⭐⭐⭐⭐⭐ | 认证/授权/加密体现？ | SQL注入/XSS/CSRF架构防护 |
| 2.5 | 性能 | ⭐⭐⭐⭐ | 有量化指标？ | 10x流量突增承载能力 |
| 2.6 | 可扩展性 | ⭐⭐⭐ | 水平扩展路径清晰？ | 数据分片后跨片查询 |
| 2.7 | 部署可行性 | ⭐⭐⭐ | 可在目标环境落地？ | 多可用区同时故障 |
| 2.8 | 量化程度 | ⭐⭐⭐⭐⭐ | 关键指标有数字？ | 无量化=无法验收 |
| 2.9 | **代码规范工具** | ⭐⭐⭐⭐⭐ | **Lint/静态分析工具已选定？** | **工具 EOL / 不维护的替代方案** |
| 2.10 | **CI 质量门禁** | ⭐⭐⭐⭐ | **Lint+类型检查集成到 CI？** | **CI 挂了仍可合并的绕过风险** |

**关键审核规则**:
- 安全性和性能必须有**量化指标**（如：P99延迟<200ms、QPS>10000）
- 组件间依赖深度不超过 N 层（建议 ≤3）
- 必须有明确的降级方案（Graceful Degradation）
- **🆕 必须在架构阶段确定代码规范工具链**（ESLint/Pylint/golangci-lint 等），并在 CI 中强制执行
- **🆕 Lint 规则不能是"全关"模式，必须启用严格规则集（如 ESLint recommended + strict, Pylint ≥9.5 分）**
- **🆕 类型检查必须在 CI 中作为阻塞门禁**（`tsc --noEmit` / `mypy --strict` / `cargo check`）

### 3.3 Phase 3: 模块设计文档审核

| # | 维度 | 权重 | 检查点 | 极端压力测试 |
|---|------|------|--------|-------------|
| 3.1 | 接口一致性 | ⭐⭐⭐⭐⭐ | 时序图↔接口1:1映射？ | 缺失接口调用的降级处理 |
| 3.2 | 数据范式 | ⭐⭐⭐⭐ | ER满足第三范式？ | 故意反范式的理由和风险 |
| 3.3 | 索引量化 | ⭐⭐⭐⭐ | 索引有覆盖分析？ | 百万级查询计划验证 |
| 3.4 | 字段完整性 | ⭐⭐⭐⭐ | 必填/可选/默认值明确？ | NULL传播导致计算错误 |
| 3.5 | 错误码体系 | ⭐⭐⭐ | 错误码完整不冲突？ | 未知错误兜底处理 |
| 3.6 | 幂等性 | ⭐⭐⭐⭐ | 写操作保证幂等？ | 网络重试双重提交 |
| 3.7 | 量化程度 | ⭐⭐⭐⭐⭐ | 字段长度/精度有数字？ | 超长输入截断行为 |
| 3.8 | **代码规范约束** | ⭐⭐⭐⭐ | **接口/模型的 Lint 规则已定义？** | **新增文件绕过 Lint 检测的风险** |
| 3.9 | **类型安全要求** | ⭐⭐⭐⭐⭐ | **接口参数/返回值有严格类型？** | **`any`/动态类型导致的运行时错误** |

**关键审核规则**:
- **🆕 接口定义必须包含类型注解的 Lint 强制规则**（如 TypeScript strictNullChecks, Python type hints 必填）
- **🆕 数据模型字段必须有长度/格式校验的 Lint 规则或 ORM 约束**
- **🆕 错误码枚举必须被 Lint 覆盖，禁止 magic number / magic string 作为错误码**

### 3.4 Phase 4: 规范文档审核

| # | 维度 | 权重 | 检查点 | 极端压力测试 |
|---|------|------|--------|-------------|
| 4.1 | 状态完备性 | ⭐⭐⭐⭐⭐ | 所有状态有进入/退出条件？ | 初始状态重复进入处理 |

| 4.3 | 规则可执行 | ⭐⭐⭐⭐⭐ | 规则足够具体可编码？ | 边界值精确行为定义 |

| 4.5 | 冲突检测 | ⭐⭐⭐⭐ | 规则间无矛盾？ | 同时触发多条规则的裁决 |

**反模式黑名单**:
- ❌ "按常规处理" → 必须明确定义常规是什么
- ❌ "视情况而定" → 必须列出所有情况和对应行为
- ❌ "适当处理错误" → 必须列出每种错误的处理方式
- ❌ "其他情况忽略" → 必须解释为什么可以安全忽略

### 3.5 Phase 5: 测试文档审核

| # | 维度 | 权重 | 检查点 | 极端压力测试 |
|---|------|------|--------|-------------|
| 5.1 | 场景覆盖率 | ⭐⭐⭐⭐⭐ | 100% Gherkin有测试？ | 隐藏组合边界条件 |
| 5.2 | 接口覆盖率 | ⭐⭐⭐⭐ | 100% API有测试？ | 参数组合爆炸最小覆盖 |
| 5.3 | 规则覆盖率 | ⭐⭐⭐⭐ | 100%规则有测试？ | 规则边界±ε偏差 |
| 5.4 | 类型分层 | ⭐⭐⭐⭐ | 单元/集成/E2E完整？ | 跨层缺陷漏测风险 |
| 5.5 | 负面测试 | ⭐⭐⭐⭐⭐ | 异常输入充分？ | Unicode/特殊字符/超长 |
| 5.6 | 数据隔离 | ⭐⭐⭐ | 测试数据独立？ | 测试间数据污染 |
| **5.7** | **🛡️ 测试神圣性** | **⭐⭐⭐⭐⭐** | **测试权威链完整？** | **"改实现 vs 改测试"的判定链断裂风险** |

**关键审核规则（Phase 5 专用）**:
- **🆕 每个测试用例必须可追溯到规范来源** (Phase 1 UC-ID / Phase 4 R-ID / Gherkin 场景)
- **🆕 断言必须精确，禁止模糊断言** (`toBeTruthy` → 精确值匹配)
- **🆕 测试文档中必须包含"失败判定流程"**: 当测试不通过时如何判定谁错了
- **🆕 明确标注哪些测试是"契约测试"（不可随意修改）vs "辅助测试"**

**5.7 测试神圣性详细检查**:

| 检查项 | 通过标准 |
|--------|---------|
| 规范追溯 | 每个 TEST-ID 都能映射到 UC-ID 或 R-ID 或 Gherkin 场景 ID |
| 断言精确度 | 无 `toBeTruthy()`/`toBeFalsy()`/`toBeUndefined()` 等模糊断言 |
| 判定流程 | 文档中包含 "测试失败→判定→处理" 的决策树 |
| 契约保护 | 标注了核心契约测试（修改需走 CR-002 变更审核） |

## 4. 极端情况压力测试方法论

### 4.1 压力测试分类体系

```
极端情况压力测试
  ├── 数据维度
  │   ├── 零值/空值/NULL
  │   ├── 最大值/溢出
  │   ├── 特殊字符 (Unicode/控制字符/Emoji)
  │   └── 超长输入 (buffer overflow 风险)
  │
  ├── 并发维度
  │   ├── 零并发 (单用户)
  │   ├── 最大并发 (容量上限)
  │   ├── 并发写入同一资源 (竞态条件)
  │   └── 分布式一致性问题 (CAP 定理边缘)
  │
  ├── 时间维度
  │   ├── 时区跨越 (UTC+/-12)
  │   ├── 闰秒/夏令时切换
  │   ├── 系统时钟回拨
  │   └── 长时间运行 (内存泄漏/连接池耗尽)
  │
  ├── 外部依赖维度
  │   ├── 单依赖失败
  │   ├── 全部依赖失败 (级联故障)
  │   ├── 依赖响应超时 (级联超时)
  │   └── 依赖返回异常数据 (毒药消息)
  │
  └── 安全维度
      ├── 未认证访问
      ├── 权限越界 (水平/垂直)
      ├── 注入攻击 (SQL/XSS/命令注入)
      └── 暴力破解 (速率限制绕过)
```

### 4.2 压力测试执行模板

```markdown
## 极端压力测试 — {文档名} — {阶段}

### 测试目标
验证 {文档} 在 {具体方面} 的鲁棒性

### 测试矩阵

| # | 测试场景 | 分类 | 预期行为 | 实际行为 | 结果 |
|---|---------|------|---------|---------|------|
| T1 | {场景描述} | 数据/并发/时间/依赖/安全 | {应如何处理} | {实际如何处理或待验证} | ⬜ |

### 重点测试场景（必测）
1. {最可能出问题的场景}
2. {历史上类似项目出过问题的场景}
3. {安全审计要求的场景}

### 压力测试结论
- 🟢 鲁棒: {n} 个场景全部通过预期
- 🟡 可接受: {n} 个场景有降级方案但非完美
- 🔴 风险: {n} 个场景存在未处理的缺陷 → 阻塞
```

## 5. 审核结果分级与处理

### 5.1 三级判定标准

| 等级 | 含义 | 条件 | 后续动作 |
|------|------|------|---------|
| **PASS ✅** | 无阻塞问题 | 0 个阻塞项 + <3 个修改建议 | 直接进入下一阶段 |
| **CONDITIONAL_PASS ⚠️** | 有非阻塞问题 | 0 个阻塞项 + ≥3 个修改建议 | 记录建议，可继续但建议尽快修复 |
| **FAIL ❌** | 有阻塞问题 | ≥1 个阻塞项 | **必须修复后重新审核** |

### 5.2 阻塞项 vs 非阻塞项判定规则

**自动阻塞（FAIL）**:
- 缺少关键图表/文档
- 存在逻辑矛盾或冲突
- 缺少量化指标（性能/安全/容量）
- 存在安全漏洞（硬编码密钥、SQL注入风险等）
- 违反 project-constraint.yaml 中的强制约束
- 反模式黑名单中的表述

**通常为非阻塞（CONDITIONAL）**:
- 格式不一致
- 描述不够详细但方向正确
- 可以后续补充的非关键信息
- �别字/语法小错误

### 5.3 审核闭环

```
文档初稿 → 审核(第一轮) → 结果?
                                │
                    ┌───────────┼───────────┐
                    ▼           ▼           ▼
                  PASS    CONDITIONAL      FAIL
                    │         │             │
                    ▼         ▼             ▼
               进入下一阶段  记录+继续     修改重审
                                        │
                                        ▼
                                   审核(第二轮)
                                        │
                                   ... (最多3轮)
                                        │
                                   ≥3轮仍未通过?
                                        │
                                        ▼
                              升级讨论: 设计本身可能有根本问题
```

## 6. 审核质量保障

### 6.1 审核员行为准则

- [ ] **客观公正**: 只基于事实和标准判断，不带个人偏好
- [ ] **逐项记录**: 每条意见都有明确的检查项编号和位置引用
- [ ] **建设性**: 每个问题都附带具体的改进建议
- [ ] **一致性**: 同类问题在不同阶段使用相同判定标准
- [ ] **时效性**: 审核应在文档完成后及时进行

### 6.2 审核防偏差机制

| 偏差类型 | 防御措施 |
|---------|---------|
| 审核疲劳（后期放松标准） | 使用结构化检查清单，逐项打勾 |
| 熟悉偏差（对自己写的文档放水） | 强制使用独立审核代理 |
| 顺序偏差（先入为主） | 随机打乱检查顺序 |
| 严重度漂移（同类问题不同判罚） | 使用固定严重度矩阵 |

### 6.3 审核记录留存

每次审核必须生成独立的审核报告文件：
```
docs/reviews/
├── review-phase1-{feature}-{date}.md
├── review-phase2-{feature}-{date}.md
...
```
包含：审核人、时间、逐项结果、最终判定、所有意见及处理状态。

## 7. 🆕 文档质量 Lint（MarkdownLint）

> **文档也是代码。SKILL.md、设计文档、README 等 `.md` 文件必须通过 MarkdownLint 检测。**

### 7.1 为什么文档需要 Lint

| 问题类型 | 示例 | 影响 |
|---------|------|------|
| **标题结构错误** | 跳级（h1→h3）、多 h1 | 目录生成错乱、渲染异常 |
| **格式不一致** | 列表风格混用、代码围栏不统一 | 可读性差、专业度低 |
| **硬 tab / 行过长** | 编辑器显示混乱 | 协作时产生无意义 diff |
| **链接失效** | 内部锚点断裂、外部链接 404 | 导航失败 |
| **尾随空格/多余空行** | Git diff 噪音 | 代码审查干扰 |

### 7.2 MarkdownLint 检测流程

```
Step 1: 探测 markdownlint 配置
  ├── .markdownlint.json / .markdownlint.yaml / .markdownlint.yml 存在? → 使用项目配置
  └── 不存在 → 使用推荐最小规则集（见下方）

Step 2: 执行检测
  └── npx markdownlint "**/*.md" --config {config}

Step 3: 审查结果分级
  ├── Error 级别 (MD001-MD014 等): ❌ 阻塞，必须修复
  └── Warning 级别: ⚠️ 记录，建议修复
```

### 7.3 推荐最小规则集

如果项目尚无 markdownlint 配置，推荐至少启用以下核心规则：

| 规则 ID | 名称 | 说明 |
|--------|------|------|
| MD001 | heading-levels | 标题层级只能递增（h1→h2→h3） |
| MD002 | first-line-heading | 第一个标题必须是 h1 |
| MD003 | heading-style | 标题格式一致（atx / setext 不混用） |
| MD004 | ul-style | 无序列表符号一致（`-` / `*` / `+`） |
| MD007 | ul-indent | 列表缩进一致 |
| MD010 | no-hard-tabs | 禁止硬 Tab 字符 |
| MD013 | line-length | 行长度限制（建议 120 或按项目约定） |
| MD025 | single-title | 单文档只允许一个 h1 |
| MD026 | no-trailing-punctuation | 标题末尾无标点 |
| MD029 | ol-prefix | 有序列表前缀序号从 1 开始 |
| MD033 | no-inline-html | 禁止内联 HTML（安全+一致性） |
| MD041 | first-line-h1 | 文件首行必须是 h1 |
| MD046 | code-block-style | 代码块围栏风格一致 |
| MD048 | code-fence-style | 代码围栏字符数一致（``` 3个或更多） |
| MD049 | emphasis-style | 强调符号一致（`*` / `_` 不混用） |

### 7.4 文档审核中的 MarkdownLint 集成

在每个阶段的**编写后审核**中增加：

| 阶段 | MarkdownLint 检查重点 |
|------|---------------------|
| Phase 1 (需求) | 标题结构正确性、链接有效性、表格格式 |
| Phase 2 (架构) | Mermaid 图表语法、代码块语言标注 |
| Phase 3 (接口) | API 文档格式、字段表格对齐 |
| Phase 5 (测试) | Gherkin 语法、代码示例格式 |
| Phase 6 (任务) | 任务列表格式、checkbox 一致性 |

## 8. 🆕 配置文件探测原则（Anti-Hallucination）

> **绝对禁止臆想项目使用的工具链和命令。所有 Lint/静态分析必须基于项目中实际存在的配置文件执行。**

### 8.1 探测优先级链

```
1. 项目根目录的显式配置文件（最高优先级）
   .eslintrc.* / eslint.config.*
   tsconfig.json
   pyproject.toml / .pylintrc / ruff.toml
   .golangci.yml
   clippy.toml
   .markdownlint.*

2. 包管理器中的 lint 配置（次优先级）
   package.json 中的 eslintConfig / prettier 字段
   pyproject.toml 的 [tool.*] 段
   Cargo.toml 的 [lint] 段

3. IDE/编辑器配置（参考，不作为执行依据）
   .vscode/settings.json
   .idea/
   ⚠️ IDE 配置 ≠ 团队规范，仅作交叉验证

4. CI/CD 流水线中的 lint 步骤（验证一致性）
   .github/workflows/*.yml
   ⚠️ 如果 CI 有 lint 但本地无配置 → 本地与 CI 不一致的警告

5. 默认值（最后手段，必须明确声明）
   仅当上述全部缺失时才使用默认严格模式
   并在报告中注明"使用默认配置"
```

### 8.2 臆想检测反模式

| 反模式 | 正确做法 |
|--------|---------|
| 直接写 `npx eslint .` 不检查是否有 .eslintrc | 先 `ls .eslintrc.* eslint.config.*` |
| 假设 Python 用 pylint | 读 `pyproject.toml` [tool] 段确认实际工具 |
| 用 `--rule` 覆盖项目配置 | 读取并尊重项目已有规则 |
| 忽略 IDE 报的错误 | 对比 IDE 配置 vs CLI 配置找出差异 |
| 报告 "lint 通过" 但未说明用的什么命令 | 在报告中记录实际执行的完整命令 + exit code |

### 8.3 配置缺失处理策略

| 场景 | 处理方式 | 严重度 |
|------|---------|--------|
| 语言文件存在 + lint 配置存在 | ✅ 读取配置后执行 | 正常 |
| 语言文件存在 + lint 配置**不存在** | ❌ **阻塞：要求先创建配置** | Critical |
| IDE 有 lint 设置但无独立配置文件 | ⚠️ **警告：IDE 规则需导出为团队配置** | Important |
| CI 有 lint 但本地无配置 | ⚠️ **警告：本地与 CI 不一致风险** | Important |
| 配置文件存在但内容为空/全关 | ❌ **阻塞：配置形同虚设** | Critical |

## 9. 🆕 原则合规性审核（Principle Compliance Review）

> **在每个阶段的编写后审核中，除了格式/内容/极端情况外，还要验证设计/编码原则是否在编写过程中被遵循。**
> **详见 `constraint-checklist.md` DP-001 ~ DP-009**

### 9.1 各阶段原则审核重点

| 阶段 | 重点审查原则 | 审查方法 |
|------|------------|---------|
| Phase 1 (需求) | — (原则主要在设计/编码阶段) | — |
| Phase 2 (架构) | SRP / OCP / DIP / KISS / YAGNI / 组合>继承 | 组件图逐个检查职责单一性、依赖方向、扩展点、复杂度 |
| Phase 3 (模块) | SRP / ISP / DIP / LoD / DRY | 接口粒度、时序图调用链深度、类型复用 |
| Phase 4 (规范) | OCP / SRP / KISS / DRY | 规则表是否支持"加不改"、规则是否单一、Gherkin 步骤复用 |
| Phase 5 (测试) | SRP / KISS | 测试是否只验证一个行为、场景步骤数是否合理 |
| Phase 6 (任务) | SRP / YAGNI / DRY | 任务是否最小功能单元、是否有冗余任务 |
| Phase 7 (代码) | **全部 9 条原则** | 函数级 SRP/DIP/LoD/KISS/YAGNI + 类级 LSP/组合 + 架构级 OCP/DRY |
| Phase 8 (集成) | DIP / LoD / DRY | 模块间耦合度、共享代码、Mock 合理性 |

### 9.2 原则违规分级处理

| 违规等级 | 定义 | 处理方式 | 示例 |
|---------|------|---------|------|
| **Critical** | 违反 OCP 或 DIP（影响扩展性和可维护性的核心） | 必须立即修复，阻塞进入下一阶段 | 硬编码 if-else 替代多态；直接 new 具体类 |
| **High** | 违反 SRP / DRY / LSP（影响代码质量的核心） | 本次必须修复 | 函数 >50 行；复制粘贴逻辑；子类破坏父类契约 |
| **Medium** | 违反 ISP / KISS / YAGNI / LoD / 组合>继承 | 建议修复，下阶段前必须处理 | 胖接口；过度设计；不必要的预留方法 |
| **Low** | 轻微偏差，但不影响正确性 | 记录即可 | 注释风格不完全符合 WHY 标准 |

### 9.3 预防式 vs 检测式 原则检查

```
检测式（不推荐）:                    预防式（本协议要求）:
  写完代码                          写代码的过程中
    ↓                                  ↓
  运行原则检查工具                     每写一个函数就问自己:
    ↓                                  - 这个函数只做一件事吗?(SRP)
  发现 5 个违规                       - 我依赖的是接口吗?(DIP)
    ↓                                  - 这是最简方案吗?(KISS)
  逐一修改                           - 有更简单的实现吗?
    ↓                                  - 为什么这样做?(BC-006)
  可能引入新问题                      → 如果有问题当场修正
  反复循环                              → 一次做对
                                     → 不需要反复改
```

## 10. 🆕 变更原因完整性审核 (WHY Completeness Review)

> **详见 `constraint-checklist.md` BC-006 + CR-001~CR-003**

### 10.1 WHY 审核在各阶段的应用

| 阶段 | WHY 审核对象 | 要求 |
|------|------------|------|
| 所有阶段 | 文档修改说明 | 修改了什么 + 为什么改 + 影响范围 |
| Phase 7+8 | Commit Message | 根因分析 + 关联 issue/PR 编号 |
| Phase 7+8 | PR/MR Description | WHY + WHAT + IMPACT + VERIFICATION 四段式 |
| Phase 7+8 | Code Review Comment | 意见必须附带原因说明 |
| Phase 7+8 | 代码内注释 | 解释 "为什么这样写" 而非 "做了什么" |

### 10.2 WHY 缺失的后果

| 场景 | WHY 缺失的影响 |
|------|--------------|
| Commit 无原因 | Git blame 无法理解变更动机，后续维护者需重新推理 |
| PR 无根因 | Reviewer 无法判断变更必要性，可能拒绝合理变更或通过有害变更 |
| 注释无 WHY | 下一个开发者不敢修改代码（不知道为什么这样设计） |
| Bug fix 无根因 | 同类 Bug 可能再次出现（未解决根本问题） |
