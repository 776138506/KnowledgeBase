>

## 🚫 流程约束（4 条）

### FC-001: 禁止跳过任何开发阶段

**规则**: 必须严格按照 10 个阶段顺序执行

```
Phase 0 → Phase 1 → Phase 2 → ... → Phase 9
```

**违规示例**:
- ❌ 直接从 Phase 0 跳到 Phase 7（编码）
- ❌ 跳过 Phase 5（规范定义）直接写代码
- ❌ 并行执行多个阶段

**正确做法**:
- ✅ 每个阶段必须按顺序完成
- ✅ 每个阶段完成后等待用户确认
- ✅ 确认后才能进入下一阶段

**检查方法**:
```bash
# 检查当前所处阶段
aifirst-prd-manager status --feature=[name]

# 应该显示当前完成的阶段和下一步
```

---

### FC-002: 禁止未确认进入下一阶段

**规则**: 必须完成上一阶段的门禁检查并获得用户确认

**门禁清单**:
- [ ] 阶段产出物已完整生成
- [ ] 质量检查全部通过
- [ ] 用户已明确确认"可以继续"
- [ ] 追溯记录已更新

**违规示例**:
- ❌ 用户说"继续"但未确认具体产出物
- ❌ 跳过用户确认直接开始下一阶段
- ❌ 用户提出修改意见但忽略并继续

**正确做法**:
- ✅ 展示完整的产出物列表
- ✅ 等待用户逐项确认
- ✅ 记录用户的修改意见并执行
- ✅ 获得明确的"可以进入下一阶段"确认

---

### FC-003: 禁止修改已确认的规范/图表

**规则**: 已通过人工确认的规范、图表、设计文档不得擅自修改

**变更流程**:
1. 提出变更申请，说明原因
2. 影响分析（哪些产出物会受影响）
3. 用户审批
4. 执行变更
5. 更新所有关联的追溯记录

**违规示例**:
- ❌ 发现代码不好写就偷偷改接口定义
- ❌ 觉得 ER 图不合理就自行修改
- ❌ 不通知用户就调整状态机状态

**正确做法**:
- ✅ 遇到问题时先与用户沟通
- ✅ 走正式的变更流程
- ✅ 更新所有受影响的文档和追溯链

---

### FC-004: 禁止无图表直接编码

**规则**: 必须先生成对应的图表/流程图，确认逻辑后再编写代码

**图表先行原则**:

| 编码任务 | 必须先有 | 对应文件 |
|---------|---------|---------|
| 函数实现 | 函数流程图 | specs/[自定义] |
| 类设计 | 类图 | specs/[自定义] |
| 接口实现 | 接口时序图 | 05-sequence.md |
| 数据操作 | ER 图 | 06-er.md |
| 状态处理 | 状态机图 | 07-state-machine.md |

**违规示例**:
- ❌ 直接写函数代码，没有流程图
- ❌ 直接建表，没有 ER 图
- ❌ 直接实现接口，没有时序图

**正确做法**:
- ✅ 先画流程图/类图
- ✅ 与用户确认逻辑正确
- ✅ 再按照图表编写代码
- ✅ 确保代码逻辑与图表一致

## 🔒 技术约束（4 条）

### TC-001: 禁止引入未授权依赖

**规则**: 只能使用 `project-constraint.yaml` 中列出的依赖库/框架

**检查方法**:
```bash
# 查看 project-constraint.yaml 中的 allowed dependencies
cat docs/project-constraint.yaml | grep dependencies

# 检查实际使用的依赖
pip list | grep -v "allowed"

# 对比差异
```

**违规示例**:
- ❌ 项目规定用 SQLAlchemy，但用了 Django ORM
- ❌ 项目规定用 FastAPI，但加了 Flask
- ❌ 私自引入新的库而不更新配置文件

**正确做法**:
- ✅ 需要新依赖时先申请
- ✅ 更新 `project-constraint.yaml`
- ✅ 通过评审后再使用

---

### TC-002: 禁止修改基础架构

**规则**: 项目的目录结构、基础架构未经授权不得修改

**保护范围**:
- `docs/` 目录结构
- `scripts/` 目录结构
- `resources/` 目录结构
- 全局配置文件格式
- 基础中间件设置

**违规示例**:
- ❌ 随意添加新的全局目录
- ❌ 修改 `docs/` 的文件命名规范
- ❌ 删除全局脚本

**正确做法**:
- ✅ 架构变更需要项目负责人授权
- ✅ 变更前进行影响评估
- ✅ 更新项目文档

---

### TC-003: 禁止跨层调用

**规则**: 必须遵循组件职责定义，禁止跨层调用

**标准分层架构**:

```
表示层 (Presentation)
    ↓ 只能调用
业务层 (Business Logic)
    ↓ 只能调用
数据访问层 (Data Access)
    ↓ 只能调用
基础设施层 (Infrastructure)
```

**违规示例**:
- ❌ Controller 直接操作数据库
- ❌ Service 直接返回 HTTP 响应
- ❌ Model 包含业务逻辑

**正确做法**:
- ✅ Controller → Service → Repository → Database
- ✅ 每层只做自己的事
- ✅ 通过依赖注入解耦

---

### TC-004: 禁止硬编码敏感信息

**规则**: 所有敏感信息必须通过配置文件或环境变量管理

**敏感信息类型**:
- 数据库连接字符串
- API 密钥
- 密码/Token
- 第三方服务凭证
- 加密密钥

**违规示例**:
```python
# ❌ 错误：硬编码
DB_HOST = "192.168.1.100"
API_KEY = "sk-xxxxx"
PASSWORD = "admin123"
```

**正确做法**:
```python
# ✅ 正确：使用配置
from pydantic import BaseSettings

class Settings(BaseSettings):
    db_host: str
    api_key: str
    
    class Config:
        env_file = ".env"

settings = Settings()
DB_HOST = settings.db_host
API_KEY = settings.api_key
```

## 👤 行为约束（4 条）

### BC-001: 禁止臆造需求/规则

**规则**: 所有实现必须严格匹配 PRD 中的规范，不得添加未定义的功能

**常见臆造行为**:
- ❌ 觉得"用户可能需要"就添加功能
- ❓ 自己猜测边界条件
- 💭 认为"这样更好"就改变原有逻辑
- 🤔 自作主张添加字段或参数

**正确做法**:
- ✅ 不确定时就问用户
- ✅ 严格按 PRD 实现
- ✅ 需要变更时走变更流程
- ✅ 记录所有假设并让用户确认

---

### BC-002: 禁止删除/修改追溯记录

**规则**: 所有历史追溯记录必须保留，删除或修改视为严重违规

**追溯记录包含**:
- trace-total.md（项目级）
- feature/trace.md（功能级）
- Git 提交历史
- 变更日志

**违规示例**:
- ❌ 删除旧的追溯条目
- ❌ 修改已提交的追溯 ID
- ❌ 清空 Git 历史
- ❌ 重写提交信息

**正确做法**:
- ✅ 错误修正时追加新记录
- ✅ 使用追加模式更新
- ✅ 保留完整的变更历史
- ✅ 标记废弃但不清除

---

### BC-003: 禁止跳过自检

**规则**: 完成任务后必须先执行自检清单，不能直接交付

**自检清单（每次完成任务后执行）**:

#### 代码质量自检
- [ ] 代码符合 PEP8 / ESLint 规范
- [ ] 无 TODO / FIXME / HACK 注释
- [ ] 无 console.log / print 调试语句
- [ ] 无硬编码的魔法数字
- [ ] 函数/方法长度 < 50 行
- [ ] 圈复杂度 < 10

#### 测试覆盖自检
- [ ] 新增代码有对应测试
- [ ] 测试覆盖主要路径
- [ ] 边界条件已测试
- [ ] 异常情况已测试
- [ ] 测试可重复运行

#### 文档完整性自检
- [ ] 函数/方法有 docstring
- [ ] 复杂逻辑有注释说明
- [ ] API 有使用示例
- [ ] 配置项有说明
- [ ] 变更有 changelog

**违规示例**:
- ❌ 写完代码就直接提交
- ❌ 测试失败也提交
- ❌ 不运行 lint 检查
- ❌ 文档缺失也交付

**正确做法**:
- ✅ 完成后立即执行自检
- ✅ 所有检查项通过后才提交
- ✅ 自检结果记录在 task-checklist.md
- ✅ 未通过项修复后重新自检

---

### BC-004: 禁止无测试代码

**规则**: 所有代码必须有对应的单元测试，禁止裸代码提交

**最低要求**:
- 每个公开函数至少 1 个测试用例
- 每个分支条件都有覆盖
- 每个异常路径都有测试
- 关键业务逻辑 100% 覆盖

**测试类型矩阵**:

| 代码类型 | 必需测试 | 可选测试 |
|---------|---------|---------|
| 工具函数 | 单元测试 | 性能测试 |
| 业务逻辑 | 单元 + 集成测试 | E2E 测试 |
| API 接口 | 集成 + E2E 测试 | 压力测试 |
| 数据模型 | 单元测试 | 迁移测试 |

**违规示例**:
- ❌ 只有代码没有测试
- ❌ 测试全是 pass 或假数据
- ❌ 只测 happy path
- ❌ 测试与实现不同步

**正确做法**:
- ✅ TDD：先写测试再写代码
- ✅ 测试覆盖正常、异常、边界
- ✅ 测试使用真实场景数据
- ✅ 代码和测试一起提交

## 🔍 违规检测机制

### 自动检测（CI/CD 集成）

```yaml
# .github/workflows/constraint-check.yml
name: AI Constraint Check

on: [pull_request, push]

jobs:
  check-constraints:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      
      - name: Check Phase Order
        run: |
          python scripts/check_phase_order.py
          # 检查是否有跳过的阶段
      
      - name: Check Diagrams Exist
        run: |
          python scripts/check_diagrams.py
          # 检查编码前是否有图表
      
      - name: Check Test Coverage
        run: |
          pytest --cov=src --cov-fail-under=80
          # 检查测试覆盖率
      
      - name: Check Trace Records
        run: |
          python scripts/check_trace.py
          # 检查追溯记录完整性
```

**技术合规性**:

## ⚠️ 违规后果

### 严重程度分级

| 级别 | 类型 | 后果 | 处理方式 |
|-----|------|------|---------|
| **P0 - 致命** | 流程约束违规 | 阻塞合并 | 必须立即修复 |
| **P1 - 严重** | 技术约束违规 | 需要讨论 | 本次必须修复 |
| **P2 - 一般** | 行为违规 | 建议修复 | 下次迭代修复 |
| **P3 - 轻微** | 格式问题 | 可接受 | 方便时修复 |
