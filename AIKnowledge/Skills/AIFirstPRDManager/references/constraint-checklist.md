# AI 强约束清单

> 29+ 条铁律，必须 100% 遵守，无例外
>
> **版本**: 2.0.0
> **用途**: AI 开发全流程强制约束（预防式执行：边做边遵循，非事后验证）

## 🚫 第一类：流程约束（4 条）

### FC-001: 禁止跳过任何开发阶段

**规则**: 必须严格按照 10 个阶段顺序执行

```
Phase 0 → Phase 1 → Phase 1.5 → Phase 2 → ... → Phase 9
```

**违规示例**:
- ❌ 直接从 Phase 0 跳到 Phase 7（编码）
- ❌ 跳过 Phase 5（规范定义）直接写代码
- ❌ 并行执行多个阶段（状态内并行除外）

**正确做法**:
- ✅ 每个阶段必须按顺序完成
- ✅ 每个阶段完成后等待用户确认
- ✅ 确认后才能进入下一阶段

---

### FC-002: 禁止未确认进入下一阶段

**规则**: 必须完成上一阶段的门禁检查并获得用户确认

**门禁清单**:
- [ ] 阶段产出物已完整生成
- [ ] 质量检查全部通过
- [ ] 用户已明确确认"可以继续"
- [ ] 追溯记录已更新
- [ ] **🆕 设计/编码原则已在该阶段编写过程中贯彻**

**违规示例**:
- ❌ 用户说"继续"但未确认具体产出物
- ❌ 跳过用户确认直接开始下一阶段
- ❌ 用户提出修改意见但忽略并继续

---

### FC-003: 禁止修改已确认的规范/图表

**规则**: 已通过人工确认的规范、图表、设计文档不得擅自修改

**变更流程**:
1. 提出变更申请，**说明原因（WHY）**——不是目的（WHAT），是根因
2. 影响分析（哪些产出物会受影响）
3. 用户审批
4. 执行变更
5. 更新所有关联的追溯记录

**正确做法**: 遇到问题时先与用户沟通，走正式的变更流程

---

### FC-004: 禁止无图表直接编码

**规则**: 必须先生成对应的图表/流程图，确认逻辑后再编写代码

| 编码任务 | 必须先有 | 对应文件 |
|---------|---------|---------|
| 函数实现 | 函数流程图 | specs/[自定义] |
| 类设计 | 类图 | specs/[自定义] |
| 接口实现 | 接口时序图 | 05-sequence.md |
| 数据操作 | ER 图 | 06-er.md |
| 状态处理 | 状态机图 | 07-state-machine.md |

## 🔒 第二类：技术约束（6 条）

### TC-001: 禁止引入未授权依赖

**规则**: 只能使用 `project-constraint.yaml` 中列出的依赖库/框架

需要新依赖时先申请 → 更新配置 → 通过评审后再使用。

---

### TC-002: 禁止修改基础架构

**规则**: 项目的目录结构、基础架构未经授权不得修改

保护范围: `docs/` / `scripts/` / `resources/` 目录结构、全局配置文件格式、基础中间件设置。

---

### TC-003: 禁止跨层调用

**规则**: 必须遵循组件职责定义，禁止跨层调用

```
表示层 → 业务层 → 数据访问层 → 基础设施层
   （每层只能调用其下一层）
```

---

### TC-004: 禁止硬编码敏感信息

**规则**: 所有敏感信息必须通过配置文件或环境变量管理

敏感信息类型: 数据库连接字符串、API 密钥、密码/Token、第三方服务凭证、加密密钥。

---

### TC-005: 禁止使用已 EOL 或废弃的技术

**规则**: 在未通过 Phase 1.5 技术栈验证的情况下进行架构设计

详见 `references/tech-stack-validation.md`。

---

### TC-006: 🆕 禁止 Lint/静态分析未通过时提交代码

**规则**: Lint 检测必须基于项目中**实际存在的配置文件**执行，禁止臆想命令

- [x] 禁止在 Lint 未通过（非 0 error/warning）的情况下提交代码
- [x] 禁止使用无理由的 lint 抑制注释（`eslint-disable` / `# noqa`）
- [x] 禁止"全关"模式的 Lint 配置
- [x] **🆕 禁止臆想项目使用的工具链或命令——必须先探测实际配置文件**
- [x] **🆕 禁止文档不经 MarkdownLint 就提交——文档也是代码**

详见 `skills/requesting-code-review/code-reviewer.md` Step 0-3。

## 👤 第三类：行为约束（6 条）

### BC-001: 禁止臆造需求/规则

**规则**: 所有实现必须严格匹配 PRD 中的规范，不得添加未定义的功能

不确定时就问用户。严格按 PRD 实现。需要变更时走变更流程。记录所有假设并让用户确认。

---

### BC-002: 禁止删除/修改追溯记录

**规则**: 所有历史追溯记录必须保留，删除或修改视为严重违规

错误修正时追加新记录。标记废弃但不清除。

---

### BC-003: 禁止跳过自检

**规则**: 完成任务后必须先执行自检清单，不能直接交付

自检包含: 代码质量 / 测试覆盖 / 文档完整性 三大类。

---

### BC-004: 禁止无测试代码

**规则**: 所有代码必须有对应的单元测试，禁止裸代码提交

TDD Iron Law: 无失败测试不写生产代码。

---

### BC-004.5: 🆕 禁止为通过测试而修改测试用例（测试神圣性原则）

**规则**: 测试是规范的守护者，不是覆盖率的奴隶。当测试失败时，必须先判定"谁错了"，再决定改什么。

**核心判定流程（每次测试失败时强制执行）**：

```
测试失败 → 进入判定流程
  │
  ├── Step 1: 测试是否正确反映了文档/规范？
  │   ├── 对照 Phase 1 (需求): 测试场景是否来自用例图？
  │   ├── 对照 Phase 4 (规范): 测试断言是否来自 Gherkin/规则表？
  │   └── 对照 Phase 5 (测试设计): 测试用例是否来自测试矩阵？
  │
  │   判定结果:
  │   ├── ✅ 测试符合文档 → **实现代码是错的** → 修改实现，不改测试
  │   └── ❌ 测试不符合文档（如：测试写错了场景/断言/预期值）
  │       → 这是**测试本身的 bug** → 可以修改测试
  │       → 但修改后必须重新验证: 新测试仍覆盖原规范要求？
  │       → 且必须在 commit message 中说明: "修正测试: 原测试未正确反映规范(#xxx)"
  │
  └── Step 2: 绝对禁止的行为（以下任一触发即违规）
      ❌ 为了让测试通过而放宽断言（如 `expect(result).toBe(undefined)` 改为 `expect(result)`）
      ❌ 删除失败的测试用例来提高通过率
      ❌ 将 `test('should fail', ...)` 改为 `test.skip('should fail', ...)`
      ❌ 在测试中加 `try/catch` 吞掉失败
      ❌ 修改测试的输入数据使其不再触发 bug 路径
      ❌ 修改预期值来匹配错误的实际输出（"对齐到错误"）
```

**三条铁律（不可违反）**:

| # | 铁律 | 说明 |
|---|------|------|
| **T-1** | **测试 ≥ 实现** | 测试的权威性高于实现。如果冲突，实现必须向测试屈服 |
| **T-2** | **文档 ≥ 测试** | 文档/规范的权威性高于测试。测试必须忠实反映文档 |
| **T-3** | **改测试必须留痕** | 如果确实需要改测试（因为测试本身有 bug），必须在 PR 中明确说明原因并经过审核 |

**典型违规场景与正确处理**:

| 场景 | ❌ 错误做法（违规） | ✅ 正确做法 |
|------|-------------------|-----------|
| 测试期望返回 `{a:1, b:2}` 但实现返回 `{a:1}` | 把测试改成 `expect(result.a).toBe(1)` | 检查规范文档 → 确认应返回 a+b → 修复实现补上 b 字段 |
| 测试检查抛出 `ValidationError` 但实现抛出 `Error` | 把测试改成 `.toThrow(Error)` | 规范定义了具体异常类型 → 修复实现使用正确的异常类 |
| 测试假设用户名为必填但规范说可选 | 把测试的输入改为必填 | 回到 Phase 1 确认需求 → 如果规范确实允许空名字 → **这时可以改测试**，但需注明 "修正测试: 与 Phase 1 用例 #UC-023 不一致" |
| 重构后 5 个测试失败了 | 把 5 个测试都改成适配新行为 | 先确认: 这 5 个测试测的是哪个规范点？→ 如果规范没变 → 实现重构破坏了契约 → 修复实现保持行为一致 |

**Anti-Pattern 黑名单**:

| 红旗信号 | 含义 | 处理 |
|---------|------|------|
| PR 中同时改动测试和实现且无明确说明 | 可能在"对齐到错误" | 打回要求分开提交并说明 |
| 测试覆盖率从 95% 掉到 80% 后又回到 95% | 可能删了测不过的测试 | 检查 git diff 中被删除的测试 |
| 大量 `skip` / `xdescribe` / `xit` 出现 | 可能隐藏了失败测试 | 全部 unskip 后重跑 |
| 测试中存在无意义的断言 (`expect(true).toBe(true)`) | 为凑覆盖率写的假测试 | 删除或替换为有意义测试 |
| `// TODO: fix this test later` | 测试有问题但被搁置 | 必须立即处理，不能推迟 |

### BC-004.6: 🆕 禁止修改任务未授权的文件（边界约束原则）

**规则**: 每个任务只能修改其明确声明要修改的文件。其他文件只能读取参考，禁止任何形式的修改。

**核心流程（每个任务执行前强制执行）**：

```
Step 1: 任务启动时明确授权文件列表
  │
  ├── 读取 task-checklist.md 中该任务的描述
  ├── 提取「修改文件」清单（显式列出）
  ├── 提取「参考文件」清单（只读）
  └── 如有歧义 → 立即向用户申请澄清，不能擅自猜测
  │
  ▼
Step 2: 实现过程中严格遵守边界
  │
  ├── ✅ 允许：修改授权列表中的文件
  ├── ✅ 允许：读取任何相关文件以理解上下文
  ├── ❌ 禁止：修改未授权的文件（即使"顺便修复"）
  ├── ❌ 禁止：重构未授权的文件（即使"改进设计"）
  └── ❌ 禁止：调整未授权文件的格式/注释/配置
  │
  ▼
Step 3: 如发现必须修改其他文件才能完成任务
  │
  ├── 立即停止当前任务
  ├── 向用户提交「边界变更申请」
  ├── 说明：为什么必须修改该文件 + 影响分析
  └── 等待用户批准 → 如批准 → 更新任务描述 → 继续
      如不批准 → 寻找不越界的替代方案
  │
  ▼
Step 4: 提交前自检
  │
  └── git diff 检查：修改的文件是否都在授权列表中？
      → 如有未授权文件 → 回滚该部分修改 → 重新提交申请
```

**三条铁律（不可违反）**：

| # | 铁律 | 说明 | 违规示例 |
|---|------|------|---------|
| **B-1** | **显式授权原则** | 任务描述中未明确列出可修改的文件 = 禁止修改 | 任务说"修改 UserService" → 只能改 UserService.java，不能"顺便"改 UserRepository |
| **B-2** | **参考≠修改权** | 可以读取任何文件来理解上下文，但读取不授予修改权 | 读了 config.yaml 理解配置 → 不能"顺便优化"配置格式 |
| **B-3** | **重构需申请** | 即使发现其他文件有代码坏味道，也不能擅自重构 | 看到 Utils 类有重复代码 → 不能"顺便"提取函数，必须单独申请重构任务 |

**典型场景与正确处理**：

| 场景 | ❌ 错误做法（违规） | ✅ 正确做法 |
|------|-------------------|-----------|
| 实现 A 功能时发现 B 文件有个 bug | 直接修复 B 文件的 bug | 记录 bug → 完成当前任务 → 单独申请新任务修复 B |
| 修改 X 类时发现 Y 类有重复代码 | "顺便"在 Y 类中提取公共函数 | 完成 X 类的修改 → 单独申请 DRY 重构任务 |
| 改接口时发现配置文件格式不统一 | 统一配置文件的缩进/格式 | 只改接口 → 单独申请配置规范化任务 |
| 实现功能时发现缺少工具函数 | 在 Utils 文件中添加工具函数 | 先确认 Utils 是否在授权列表中 → 如不在 → 申请或在该功能文件内实现私有辅助函数 |
| 发现公共组件有设计问题 | "顺便"重构公共组件 | 完成当前功能 → 单独申请组件重构任务（影响面评估） |

**Anti-Pattern 黑名单**：

| 红旗信号 | 含义 | 处理 |
|---------|------|------|
| PR 中修改了 task 描述未提及的文件 | 越界修改 | 打回要求说明授权来源或回滚 |
| "顺便修复了..." / "顺便重构了..." | 典型的边界侵犯 | 警告 + 要求分拆为独立 PR |
| 一个任务修改了 5+ 个文件 | 可能超出授权范围 | 逐个文件检查授权链 |
| 配置文件/公共组件被修改 | 高风险越界 | Critical: 必须单独申请 |
| 注释/格式调整出现在非授权文件 | 隐性越界 | 要求回滚 |

**文档修改特殊规则**：

文档的修改需要**额外申请**，即使该文档与任务相关：

| 文档类型 | 修改规则 |
|---------|---------|
| 设计文档（Phase 1-6 产出） | 必须走 FC-003 变更流程，不能因实现需要直接修改 |
| API 文档 | 如 API 变更 → 先申请更新 API 设计 → 再实现 |
| README/操作手册 | 单独申请文档任务，不与代码任务合并 |
| 注释 | 只能修改授权文件内的注释，不能修改其他文件的注释 |

### BC-005: 禁止无验证证据声明完成

**规则**: 任何任务的"完成"声明必须附带新鲜验证证据

运行完整测试套件 → linter → build → VCS diff 检查 → 全部通过才可声明完成。

### BC-006: 🆕 禁止只讲目的不讲原因

**规则**: 任何修改（代码/文档/配置）都必须清楚说明**原因（WHY）**，而非仅描述**目的（WHAT）**

**适用范围（全场景强制）**:

| 场景 | 要求 | 示例 |
|------|------|------|
| **Git Commit Message** | 必须包含 WHY | ❌ "fix login bug"<br>✅ "fix login: token过期后未刷新导致401(#123)，根因是refresh逻辑遗漏了error branch" |
| **PR / MR Description** | 必须包含变更原因和影响面 | ❌ "实现用户注册功能"<br>✅ "实现用户注册：当前用Excel手动录入用户效率低且易出错(日均20条录入错误)，改为自助注册流程，影响auth模块和user service" |
| **Code Review Comment** | 审查意见必须说明原因 | ❌ "改成这样"<br>✅ "改成switch: 当前if-else链已有7个分支且每分支逻辑独立，switch更易读且便于未来扩展(#45)" |
| **代码内注释** | 非"做什么"，而是"为什么这样做" | ❌ "// 设置超时为30秒"<br>✅ "// 30s: 后端API P99延迟=1.8s，留足余量避免客户端误判超时(见SRE-2024-Q3报告)" |
| **文档修改** | 变更说明需含原因 | ❌ "更新了接口文档"<br>✅ "更新接口文档: v2 API 新增了rate_limit字段(#89)，此前客户端无法感知限流状态导致重试风暴" |
| **Config 变更** | 配置改动需解释触发原因 | ❌ "timeout改成了5000"<br>✅ "timeout 3000→5000: 生产环境DB主从切换期间观察到偶发超时(#ops-442)" |
| **Bug Fix** | 必须包含根因分析 | ❌ "修复空指针问题"<br>✅ "修复NPE: UserService.findByEmail()在email=null时返回null但上层未做null check(#201)。根因: 缺少@NotNull注解+防御性校验" |

**判断标准 —— 你的修改说明是否通过了 WHY 测试？**

```
问自己三个问题:

1. 只看你的说明，不知道原始问题的人能理解为什么要改吗？
   → 如果不能 → 说明只讲了 WHAT（做了什么），没讲 WHY（为什么改）

2. 把说明中的原因删掉，剩下的部分是否还有价值？
   → 如果没有 → 说明原因是核心，但你可能没写清楚

3. 一个新人看到这个说明，能否复现你当时的思考过程？
   → 如果不能 → 说明缺少推理链条
```

**Anti-Pattern 黑名单**:

| ❌ 差的说明 | ✅ 好的说明 |
|-----------|-----------|
| "优化代码" | "优化: 将O(n²)嵌套循环改为HashMap查找，因用户列表从100增长到10000后查询耗时从2s→12s(#perf-33)" |
| "修复bug" | "修复: 并发写入时数据丢失(#156)。根因: 缺少行级锁，两个事务同时update同一行导致last-write-wins" |
| "重构" | "重构: AuthService拆分为LoginService+RegisterService(+DP-001 SRP)，原类有8个public方法职责混杂，每次修改都影响不相关功能(#tech-debt-08)" |
| "调整配置" | "调整: pool_size 10→50(#ops-22)。原因: 大促期间连接池耗尽导致P99延迟从50ms飙到2s" |
| "更新文档" | "补充: 缺失的异常场景(#review-11)。Code Review发现HTTP 503未处理，会导致上游无限重试" |

## 📐 第四类：🆕 设计/编码原则约束（9 条）

> **核心理念: 预防式执行 —— 在编码/设计/写文档的过程中就遵循这些原则，而非写完后再验证反复修改。**
> **"能一次做对就不要反复改。"**

### DP-001: 单一职责原则 (SRP — Single Responsibility Principle)

**规则**: 一个类/模块/函数/组件应该只有一个引起它变化的原因

**在编写过程中自检**（写完每个类/函数/文件时立即问自己）：

```
□ 这个类/函数是否只做一件事？
□ 如果需求变化，是否只有一个修改点？
□ 能否用一句话描述它的职责？（如果不能 → 违反SRP）
□ 这个类的所有方法是否服务于同一个业务目标？
```

**违反信号（写的过程中就要识别）**:
- 函数名包含 "and"（如 `validateAndSaveAndNotify()`）
- 类名模糊（如 `Utils`、`Helper`、`Manager`、`Processor`）
- 修改一个功能时总是需要同时改动另一个不相关的功能
- 注释里写着 "这部分处理X，那部分处理Y"

**各阶段贯彻要点**:

| 阶段 | SRP 检查动作 |
|------|-------------|
| Phase 2 架构设计 | 每个组件只能有一个变更驱动因素 |
| Phase 3 模块设计 | 每个接口只封装一种能力 |
| Phase 7 编码实现 | 每个函数 ≤ 20 行，只做一件事；每个类只服务于一个业务概念 |
| Phase 8 集成验证 | 组件间耦合度检查：修改 A 是否意外影响了 B？ |

---

### DP-002: 开闭原则 (OCP — Open/Closed Principle)

**规则**: 对扩展开放，对修改关闭。新增功能通过扩展实现，而非修改已有代码

**在编写过程中自检**：

```
□ 加新功能时，我是加了新代码还是改了旧代码？
□ 如果要加一个新的业务规则，是否能不修改已有逻辑？
□ 是否使用了策略模式/模板方法模式/插件机制来支持扩展？
□ switch/if-else 是否可以通过多态消除？
```

**各阶段贯彻要点**:

| 阶段 | OCP 检查动作 |
|------|-------------|
| Phase 2 架构设计 | 插件化架构、事件驱动、策略注入点预埋 |
| Phase 4 规则定义 | 业务规则表驱动（数据即逻辑），非硬编码 if-else |
| Phase 7 编码实现 | 新功能 = 新类/新函数/新配置，不改已有逻辑 |
| Phase 9 验收 | 验证新增功能未破坏已有功能（回归测试全绿） |

---

### DP-003: 里氏替换原则 (LSP — Liskov Substitution)

**规则**: 子类必须能够完全替换父类，且程序行为不变

**在编写过程中自检**：

```
□ 子类是否加强了前置条件？（如父类接受int，子类只接受positive int → 违反）
□ 子类是否弱化了后置条件？（如父类保证返回非null，子类可能返回null → 违反）
□ 子类是否抛出了父类不会抛出的异常？（→ 违反）
□ 用子类替换父类后，现有测试是否全部通过？（→ 最终验证）
```

**常见违反模式（写代码时要主动避免）**:
- 子类重写方法但抛出父类没有的异常
- 子类在重写方法中添加了额外的前置条件检查
- 子类返回了比父类"更少"的东西（如父返回 List，子返回 null）
- 使用 `instanceof` 在运行时区分子类型来走不同逻辑

---

### DP-004: 接口隔离原则 (ISP — Interface Segregation)

**规则**: 客户端不应该被迫依赖它不使用的方法。接口应该小而专一

**在编写过程中自检**：

```
□ 这个接口的方法是否都会被同一个调用者用到？
□ 是否存在"胖接口"——实现了许多不需要的方法？
□ 能否将大接口拆分为多个职责单一的小接口？
□ 依赖方是否只依赖它需要的最小接口？
```

**实践方法**:
- 接口方法数 ≤ 5 个（建议）
- 如果发现某个实现类中有大量 `throw new UnsupportedOperationException()` → 接口太胖
- 如果某个调用者只用到了接口 20% 的方法 → 接口应该拆分

---

### DP-005: 依赖倒置原则 (DIP — Dependency Inversion)

**规则**: 依赖抽象，不依赖具体。高层模块不应依赖低层模块，两者都应依赖抽象

**在编写过程中自检**：

```
□ import 语句中是否有具体的实现类？（应导入接口/抽象类）
□ 是否使用了依赖注入（构造函数注入 / 方法注入）而非内部 new？
□ 能否在不修改调用者代码的情况下替换底层实现？
□ 是否有 Service Locator 反模式？（→ 应该用 DI）
```

**各阶段贯彻要点**:

| 阶段 | DIP 检查动作 |
|------|-------------|
| Phase 2 架构设计 | 依赖方向：具体 → 抽象 → 具体（倒置） |
| Phase 3 接口设计 | 先定义接口契约，再实现具体类 |
| Phase 7 编码实现 | 通过构造函数注入依赖，禁止在方法内部 `new` 具体类 |
| Phase 8 集成测试 | Mock 底层依赖测试高层逻辑 |

---

### DP-006: KISS 原则 (Keep It Simple, Stupid)

**规则**: 保持简单。如果两种方案都能工作，选更简单的那个

**在编写过程中自检**：

```
□ 这个方案是不是过度设计了？
□ 有没有更简单的方式达到同样效果？
□ 引入的这个抽象/模式/框架是否真的有必要？
□ 团队中最初级开发者能看懂这段代码吗？
```

**KISS vs 过度工程的判断标准**:

| 场景 | KISS 做法 | 过度工程做法（避免） |
|------|---------|-------------------|
| 3个if-else | 保持 if-else | 引入策略模式 + 工厂 + 配置驱动 |
| 2个类有重复代码 | 先提取公共函数 | 立刻搞个通用框架 |
| 数据转换 | 写明确的转换函数 | 搞个通用的 TypeConverter<TFrom, TTo> |
| 配置管理 | 用 JSON/YAML 文件 | 搞分布式配置中心 + 热加载 + 版本控制 |

**YAGNI 边界**: 如果你现在不需要，就不要做。但如果你**确定**下周就需要，可以提前准备。

---

### DP-007: DRY 原则 (Don't Repeat Yourself)

**规则**: 每一块知识/逻辑在系统中必须有唯一、明确的表示

**在编写过程中自检**：

```
□ 这段代码是否在其他地方已经存在？（Ctrl+F 搜索一下）
□ 我是否在复制粘贴？如果是在复制 → 应该提取为共享函数/类
□ 修改这个逻辑时，是否需要同时修改其他地方？（如果 → 违反DRY）
□ 这里的"重复"是真的逻辑重复，还是只是看起来像？（偶然重复 ≠ 真正违反DRY）
```

**DRY vs 偶然重复**:
- **真正违反 DRY**: 同一业务规则的多次实现（如"用户名长度限制=32"出现在 validator + DB schema + frontend 三处）
- **偶然重复可接受**: 两个不同模块恰好有相似的但不相关的代码（如 User.validate() 和 Product.validate() 格式相似但规则完全不同）
- **误用 DRY 的反面**: 为了消除重复而引入不必要的抽象层（违反 KISS）

---

### DP-008: YAGNI 原则 (You Aren't Gonna Need It)

**规则**: 不要实现你当前不需要的功能

**在编写过程中自检**：

```
□ 这个功能/参数/配置项是当前需求明确要求的吗？
□ 还是我觉得"以后可能会用到"？
□ 如果去掉这个"预留"功能，当前需求是否受影响？
□ 这个抽象层是为了解决当前问题，还是为了想象中的未来问题？
```

**YAGNI 检查清单（Phase 1 头脑风暴时重点排查）**:
- [ ] 这个功能是否在当前 MVP/迭代范围内？
- [ ] 是否有用户故事或需求条目支撑？
- [ ] "以后可能需要" ≠ 现在需要
- [ ] 预留接口/参数/扩展点的维护成本是否值得？

**YAGNI 不等于不做设计**: 你可以做良好的架构设计来支持未来的变化，但不要**实现**那些尚未需要的功能。

---

### DP-009: 组合优于继承 (Composition Over Inheritance) + 迪米特法则 (LoD)

**规则 A — 组合优于继承**: 优先使用组合（has-a）而非继承（is-a）来表达关系

```
□ 我用继承是因为真的是 "is-a" 关系，还是只是为了复用代码？
□ 如果只是想复用代码 → 用组合（把对象作为成员变量）
□ 继承层次是否超过 3 层？（超过 → 考虑用组合替代）
□ 子类是否只覆写了少量方法却继承了大量不需要的行为？
```

**规则 B — 迪米特法则 (Law of Demeter)**: 最少知识原则。一个对象应该对其他对象有尽可能少的了解

```
□ 我的代码是否存在 a.getB().getC().doSomething() 这种链式调用？（→ 违反 LoD）
□ 我是否直接访问了朋友对象的内部状态？（应该通过方法访问）
□ 一个类是否知道太多其他类的细节？（→ 耦合度过高）
```

**迪米特法则实践**: 只和直接的朋友对话：
- 对象本身 (this)
- 方法参数
- 方法内创建的对象
- 对象的成员变量（复合对象）
- **不应该**: 成员变量的成员变量、方法返回值的内部结构

## 🔍 第五类：🆕 变更审核约束（3 条）

> **核心理念: 任何变更（代码/文档/配置/约束）都必须经过审核，且必须说清楚原因。**

### CR-001: 任何变更必须审核

**规则**: 项目中任何文件的修改都必须经过审核才能生效，无例外

**适用范围（全覆盖）**:

| 变更类型 | 审核要求 | 审核者 |
|---------|---------|--------|
| **源代码变更** (.py/.ts/.go/.rs 等) | Code Review（双阶段: Spec + Quality） | Code Quality Reviewer |
| **测试代码变更** | 与源代码同等审查标准 | Spec Reviewer + Quality Reviewer |
| **文档变更** (.md) | 文档审核（含 MarkdownLint） | Document Reviewer |
| **配置文件变更** (.yaml/.json/.toml/.env 等) | 影响分析 + 配置审查 | Config Reviewer |
| **约束文件变更** (constraint-checklist 等) | 影响面评估 + 全回归风险审查 | Architect / 用户本人 |
| **模板文件变更** (*.template) | 向后兼容性审查 + 已有实例影响评估 | Template Owner |
| **Skill 定义变更** (SKILL.md) | 行为影响分析 + 回归测试 | Skill Owner |
| **依赖变更** (package.json/go.mod/Cargo.toml) | 安全扫描 + 许可证审查 + 兼容性审查 | Dependency Reviewer |
| **CI/CD 流水线变更** | Pipeline dry-run + 安全审查 | DevOps Reviewer |

**审核最低要求**:
- [x] 变更内容已被审阅（逐行/diff 级别）
- [x] 变更**原因**已说明（WHY，符合 BC-006 标准）
- [x] 影响**范围**已评估（哪些模块/功能会受影响）
- [x] **测试**已验证（相关测试通过 + 回归测试通过）
- [x] **Lint**已通过（基于实际配置文件执行）

---

### CR-002: 变更必须说明原因（WHY > WHAT）

**规则**: 见 BC-006 详细定义。此处强调在变更审核场景的特殊要求：

**PR/MR 描述必须包含**:

```markdown
## 变更原因 (WHY)
{根因分析：是什么问题触发了这次变更？}

## 变更内容 (WHAT)
{具体改了什么}

## 影响范围 (IMPACT)
{会影响哪些模块/功能/用户？}

## 验证方式 (VERIFICATION)
{如何证明变更正确且无副作用？}
```

**如果变更描述中缺少 WHY → 直接打回，不予审核**。

---

### CR-003: 禁止绕过审核

**规则**: 以下行为视为严重违规：

- [x] **禁止** 直接 push 到 main/master 分支（必须经过 PR/MR 审核）
- [x] **禁止** 在 commit message 中加 `[skip ci]` / `[ci skip]` 跳过 CI 门禁
- [x] **禁止** 自行 merge 自己的 PR/MR（必须有第二人 approve）
- [x] **禁止** 用 `--no-verify` 跳过 pre-commit hooks
- [x] **禁止** 修改 `.gitignore` 来排除文件以逃避 Lint/检测
- [x] **禁止** 在紧急情况下"先上线再补流程"（紧急 != 可以跳过流程）

**真正的紧急流程**（仍需审核，但可加速）：
1. 紧急声明（附事故单号/监控告警链接）
2. 最小变更集（只修问题，不加其他改动）
3. 加速审核（通知 on-call 工程师优先 review）
4. 上线后补齐所有文档和流程
