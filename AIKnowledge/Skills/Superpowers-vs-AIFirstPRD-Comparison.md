## 1. 框架概览

### 1.1 Superpowers 一句话定位

**AI 编码工作流引擎** — 以 TDD 为铁律、Subagent 驱动执行、系统化调试为核心的敏捷开发方法论。

### 1.2 AIFirstPRDManager 一句话定位

**PRD→可执行契约转换器** — 以图表先行、全链路追溯、11阶段强约束流水线为特征的规范化开发范式。

### 1.3 基本信息

| 维度 | Superpowers | AIFirstPRDManager |
|------|-------------|-------------------|
| **来源** | obra/superpowers (开源社区) | 自研（基于 AI-First PRD 模板） |
| **版本** | 持续迭代（94% PR 拒绝率文化） | v1.1.0 |
| **技能数量** | 15 个独立技能 | 1 个主技能 + 5 个参考文档 |
| **阶段数** | 7 步基本工作流 | 11 阶段（含 Phase 1.5） |
| **设计模式** | Subagent + Reviewer + Inversion | Pipeline + Inversion + Reviewer |
| **目标用户** | AI Agent（Claude/Cursor/Gemini 等） | AI Agent + 人类开发者协作 |
| **核心理念** | TDD / YAGNI / DRY / 证据优先 | 图表先行 / 全链路追溯 / 强约束 |
| **文档风格** | 轻量、实用主义、反模式清单 | 重型、结构化、模板驱动 |

### 2.2 核心差异本质

| 差异维度 | Superpowers | AIFirstPRDManager |
|---------|-------------|-------------------|
| **关注焦点** | **怎么做**（How）— 编码执行质量 | **做什么**（What）— 需求到实现的完整链路 |
| **质量保障手段** | TDD 红绿循环 + 双阶段审查 | 门禁机制 + 图表约束 + 追溯体系 |
| **对 AI 的态度** | AI 是**执行者**，需要严格约束防跑偏 | AI 是**协作者**，需要结构化引导防跳步 |
| **文档产出观** | 轻文档，够用即可 | 重文档，完整可审计 |
| **变更应对** | 快速迭代，小步快跑 | 严格变更流程，留痕可溯 |
| **错误处理哲学** | 先找根因再修（Systematic Debugging） | 错误闭环迭代（Reproduce→Trace→Fix→Update） |

## 4. 逐维度深度对比矩阵

### 4.1 流程管控维度

| 评估项 | Superpowers | AIFirstPRDManager | 优胜方 |
|-------|-------------|-------------------|--------|
| **流程刚性** | 松耦合，7步可灵活组合 | 强流水线，11阶段不可跳跃 | AIFirst（需严格场景）|
| **门禁密度** | 1个 HARD-GATE (brainstorming) | 10个人工确认门禁 | AIFirst |
| **回退机制** | 无显式回退，靠审查拦截 | 错误诊断闭环迭代 | AIFirst |
| **并行能力** | dispatching-parallel-agents 技能 | 串行 Pipeline，不支持并行 | **Superpowers** |
| **循环支持** | 天然迭代循环（⑦→①） | 线性单次执行（需手动重启） | **Superpowers** |
| **中断恢复** | 每个 task 独立，易恢复 | 阶段状态需人工记录 | **Superpowers** |

### 4.2 文档产出维度

| 评估项 | Superpowers | AIFirstPRDManager | 优胜方 |
|-------|-------------|-------------------|--------|
| **设计文档** | 1份 design doc (markdown) | 9种图表文档(用例/活动/组件/PERT/序列/ER/状态机/规则/Gherkin) | AIFirst（重型项目）|
| **任务文档** | 1份 plan (超细粒度) | task-checklist.md + PERT图 | 各有千秋 |
| **代码文档** | 依赖代码自身+测试 | 流程图+类图+代码+测试 四件套 | AIFirst |
| **追溯文档** | Git commit history | 全链路 ID 关联体系 (UC→C→T→API→R→S→TEST→CODE) | **AIFirst** |
| **交付物总量** | 轻（2-3份核心文档） | 重（15+份结构化文档） | 视场景而定 |

### 4.3 测试策略维度

| 评估项 | Superpowers (TDD) | AIFirstPRDManager | 分析 |
|-------|-------------------|-------------------|------|
| **核心理念** | **无失败测试不写代码** | 先设计测试用例，后实现代码 | 目标一致，路径不同 |
| **编写时机** | 实现前一刻（Red） | 设计阶段（Phase 6） | TDD 更敏捷 |
| **覆盖策略** | 行为驱动，逐步累积 | 场景矩阵驱动，一次性规划 | AIFirst 更全面 |
| **测试类型** | 单元测试为主（TDD天然倾向） | 单元+集成+E2E 三层覆盖 | **AIFirst** |
| **与代码关系** | 测试→代码 1:1 同步生长 | 测试设计→代码实现 分离执行 | 各有优势 |
| **重构保障** | 绿灯保护（修改必保持通过） | 回归测试套件保护 | 相当 |

**关键洞察**：

```
TDD 循环 (Superpowers):          AIFirst 测试策略:
                                 
  Red ──▶ Green ──▶ Refactor     Phase 6: 设计全部测试用例
   ↑                      │             │
   └──────────────────────┘             ▼
         循环                      Phase 7: 实现代码+单元测试
                                       │
                                       ▼
                                    Phase 8: 集成测试+E2E
                                    
TDD: 渐进式，每步有安全网            AIFirst: 规划式，整体有蓝图
适合: 探索性开发、快速迭代           适合: 需求明确、合规要求高
```

### 4.4 执行模式维度

| 评估项 | Superpowers | AIFirstPRDManager | 差异说明 |
|-------|-------------|-------------------|----------|
| **执行主体** | 主 Agent + N 个 Subagent | 单一 Agent 顺序执行 | **根本性差异** |
| **上下文管理** | 每个 Subagent 全新上下文 | 单一上下文持续累积 | Subagent 更干净 |
| **模型选择策略** | 按任务复杂度动态选择 | 未定义（依赖宿主环境） | **Superpowers 更精细** |
| **审查机制** | 双阶段（规范合规+代码质量） | 单阶段（人工门禁确认） | **Superpowers 更严谨** |
| **并发能力** | 支持并行 Subagent | 不支持 | **Superpowers** |
| **故障隔离** | 单个 task 失败不影响其他 | 阶段失败阻塞后续所有 | **Superpowers** |

### 4.5 错误处理维度

| 评估项 | Superpowers (systematic-debugging) | AIFirstPRDManager (error-diagnosis) |
|-------|------------------------------------|-------------------------------------|
| **核心原则** | **无根因不修复** | **错误闭环迭代** |
| **阶段数** | 4 阶段（根因调查→模式分析→假设测试→实施修复） | 5 步（复现→追踪→分类→修复→更新约束） |
| **强制力度** | Iron Law：未完成 Phase 1 不能提出修复 | 门禁约束：必须完成诊断流程 |
| **多组件处理** | 在每个组件边界添加诊断 instrumentation | 通过追溯 ID 定位问题模块 |
| **修复次数限制** | ≥3次失败 → 质疑架构 | 未定义硬性限制 |
| **架构质疑触发** | 每次修复暴露新问题在不同位置 | 未显式定义 |

**Systematic Debugging 四阶段详解**：

```
┌─────────────────────────────────────────────────────────────────┐
│              Systematic Debugging 四阶段                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Phase 1: ROOT CAUSE INVESTIGATION (根因调查)                   │
│  ├── 1.1 仔细阅读错误信息（不跳过！）                            │
│  ├── 1.2 一致性复现（能稳定触发吗？）                            │
│  ├── 1.3 检查最近变更（git diff, 新依赖）                        │
│  ├── 1.4 多组件系统：在每个边界添加诊断日志                      │
│  └── 1.5 数据流反向追踪（从症状追溯到源头）                      │
│                                                                 │
│  Phase 2: PATTERN ANALYSIS (模式分析)                           │
│  ├── 2.1 找到正常工作的类似代码                                   │
│  ├── 2.2 对照参考实现完整阅读（不能略读！）                        │
│  ├── 2.3 列出每一个差异（无论多小）                               │
│  └── 2.4 理解依赖关系和环境假设                                   │
│                                                                 │
│  Phase 3: HYPOTHESIS & TESTING (假设与测试)                      │
│  ├── 3.1 形成单一假设（"我认为 X 是原因因为 Y"）                  │
│  ├── 3.2 最小化测试（一次只改一个变量）                            │
│  ├── 3.3 验证结果（成立→Phase4，不成立→新假设）                   │
│  └── 3.4 承认不知道（不要假装懂了）                               │
│                                                                 │
│  Phase 4: IMPLEMENTATION (实施修复)                              │
│  ├── 4.1 创建失败的测试用例（必须！）                             │
│  ├── 4.2 实施单一修复（不在同一时间做"顺便改进"）                 │
│  ├── 4.3 验证修复（原测试通过？无回归？）                         │
│  ├── 4.4 连续失败≥3次 → 停下来质疑架构！                         │
│  └── 4.5 记录并讨论后再继续                                      │
│                                                                 │
│  ⚡ 效果数据:                                                   │
│  - 系统化方法: 15-30 分钟修复                                    │
│  - 随机修复: 2-3 小时反复试错                                    │

### 7.2 具体融合改造点

#### 改造点 1: Phase 1 注入 brainstorming 技巧

```diff
### Phase 1: 调研 → 可视化场景确认

+ ## 融合: Superpowers brainstorming 技巧
+
+ ### 苏格拉底式提问协议 (来自 brainstorming/SKILL.md)
+
+ **核心原则**:
+ - 一次只问一个问题（禁止连珠炮）
+ - 给出 2-3 个方案供选择（而非开放式问题）
+ - YAGNI 原则： ruthlessly 剔除不需要的功能
+ - 增量验证：每步确认后再深入
+
+ **Anti-Pattern 警告**:
+ - ❌ "这太简单了不需要设计" → 每个项目都必须走完设计流程
+ - ❌ 直接给出最终方案 → 应先探索再收敛
+ - ❌ 忽略"不做"的边界 → 必须明确排除项
+
+ **可选工具**: Visual Companion (浏览器端原型/图表辅助)
```

#### 改造点 2: Phase 3 注入 writing-plans 细粒度

```diff
### Phase 3: 任务分解 → 关键路径确认

+ ## 融合: Superpowers writing-plans 技巧
+
+ ### 细粒度任务编写标准 (来自 writing-plans/SKILL.md)
+
+ **粒度要求**: 每个步骤 = 2-5 分钟工作量
+ （AIFirst 原标准: 1-2 天/任务 → 用于粗粒度规划）
+ （融合后: 两级规划 — AIFirst天级 → Superpowers分钟级）
+
+ **无占位符规则** (绝对禁止):
+ - ❌ TBD / TODO / 待定
+ - ❌ "添加适当的错误处理"
+ - ❌ "类似 Task N 的做法"
+ - ❌ 任何模糊描述
+
+ **任务结构模板**:
+ ```
+ ### Task X.Y: [具体动作]
+ **文件**: exact/path/to/file.ts
+ **操作**: 精确的代码变更（完整代码，非伪代码）
+ **验证**: `npm test -- --grep "exact test name"` + 预期输出
+ **命令**: `git add . && git commit -m "task(x.y): description"`
+ ```
```

#### 改造点 3: Phase 7 替换为 Subagent 驱动

```diff
- ### Phase 7: 小逻辑实现 → 逻辑先行编码
+ ### Phase 7: Subagent 驱动实现 (融合 Superpowers 执行引擎)
+
+ ## 融合: subagent-driven-development 执行模式
+
+ ### 前置条件
+ 1. **必须**先完成 git worktree 隔离 (using-git-worktrees)
+ 2. **必须**有 writing-plans 格式的任务清单
+ 3. **必须**有 Phase 5 的规范定义作为审查基准
+
+ ### Per-Task 执行循环
+
+ 对于 Plan 中的每个 Task:
+
+ **Step 1: 派遣实现者子代理 (Implementer)**
+ - 输入: task 描述 + 规范引用 (Phase 5 Gherkin/规则) + 上下文
+ - 执行模式: **TDD 红绿重构循环**
+   - RED: 先写失败测试 (参照 Phase 6 测试用例)
+   - GREEN: 写最小代码使测试通过
+   - REFACTOR: 在绿灯保护下优化
+ - 输出: DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED
+
+ **Step 2 (如有问题): 交互解决**
+ - NEEDS_CONTEXT → 收集更多信息后重新派遣
+ - BLOCKED → 报告阻塞原因，跳过或取消任务
+
+ **Step 3: 派遣规范审查者 (Spec Reviewer)**
+ - 检查维度: 是否符合 Phase 5 规范 / Phase 4 接口定义
+ - 输出: COMPLIANT / NEEDS_CHANGES
+ - 不合规 → 返回 Step 1 修改
+
+ **Step 4: 派遣代码质量审查者 (Code Quality Reviewer)**
+ - 检查维度: 代码质量 / 安全 / 性能 / 最佳实践
+ - 输出: APPROVED / NEEDS_IMPROVEMENT
+ - 不通过 → 返回 Step 1 修改
+
+ **Step 5: 标记完成 → 下一个 Task**
+
+ ### 模型选择策略
+ | 任务类型 | 推荐模型 | 理由 |
+ |---------|---------|------|

+           └── ≥3次失败 → 触发架构质疑 (暂停并升级讨论)
+ ```

## 8. 适用场景指南

### 8.1 选择决策树

```
你的项目是什么类型？
        │
        ├── 需要严格合规/审计/交付证明？
        │   └── YES → 使用 AIFirstPRDManager (原生)
        │              理由: 重型文档 + 全链路追溯满足合规要求
        │
        ├── 快速原型/MVP/探索性开发？
        │   └── YES → 使用 Superpowers (原生)
        │              理由: 轻量快速 + TDD保证质量 + 迭代友好
        │
        ├── 中大型项目 + 高质量要求？
        │   └── YES → 使用 **AIFirst-Powered Superpowers (融合版)**
        │              理由: 设计深度(AIFirst) + 执行质量(Superpowers)
        │
        └── 团队已有成熟流程，只需AI辅助？
            └── YES → 按需选取技能组合
               - 需求分析差 → 取 brainstorming + Phase 1
               - 代码质量差 → 取 TDD + subagent-dev + review
               - 调试效率低 → 取 systematic-debugging
               - 文档不规范 → 取 AIFirst Phase 2-6
```

### 8.2 场景匹配表

| 项目特征 | 推荐方案 | 理由 |
|---------|---------|------|
| 金融/医疗/政务合规项目 | **AIFirst 原生** | 审计追溯是刚需 |
| 创业公司 MVP | **Superpowers 原生** | 速度优先，TDD 保底线 |
| 企业级 SaaS 平台 | **融合版** | 设计深度 + 执行质量双重要求 |
| 内部工具/脚本开发 | **Superpowers 原生** | 轻量够用 |
| 开源库/框架开发 | **融合版** | 需要 API 设计规范 + 代码质量 |
| 学习/教学项目 | **AIFirst 原生** | 完整流程展示软件工程最佳实践 |
| 紧急 Bug 修复 | **Superpowers systematic-debugging** | 快速定位根因 |
| 大规模重构 | **融合版 Phase 2-7** | 架构设计指导 + TDD 保护重构 |
