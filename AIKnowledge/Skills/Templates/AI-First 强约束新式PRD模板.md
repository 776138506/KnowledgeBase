# AI-First 强约束新式PRD模板

## 1. 核心理念：从传统 PRD 到 AI 可执行契约

传统 PRD 是写给人看的 “需求说明书”，依赖人的经验解读，在 AI 辅助开发场景下极易导致**需求走样、AI 幻觉、流程跳步、错误难追溯**。

本新式 PRD 将传统 PRD 与**Skill 级强约束、图表驱动开发、全链路可追溯**深度融合，将其升级为**人与 AI 共同遵守的可执行契约**：

- **AI 可解析**：所有规则、流程、约束结构化，AI 能严格执行，杜绝 “凭感觉生成”

- **流程强固化**：强制遵循 “图表先行、逻辑后码”，禁止 AI 跳过设计直接写代码

- **错误可溯源**：从需求到代码全链路关联，出问题可一键定位到具体阶段

- **能力可沉淀**：每个功能的开发经验可沉淀为约束，避免重复踩坑

- **功能即 Skill**：每个功能独立闭环，拥有自己的完整规范、流程、校验，达到 Skill 级的严谨性与复用性

## 2. 新式 PRD 标准目录结构

每个独立功能（即一个 Skill 级单元）拥有独立的 PRD 目录，结构如下，AI 必须严格遵循此结构组织产出：

```text

项目根目录与单个功能目录完整结构【先明确层级关系】
# 项目根目录（全局复用，所有功能共享）
project/
├ docs/                # 项目级文档（所有功能共享，替代单个功能重复文件）
│  ├ project-constraint.yaml # 项目全局技术约束（统一技术栈、依赖版本、禁止项，替代单个功能的tech-constraint.yaml）
│  └ trace-total.md    # 项目全局追溯总表（汇总所有功能追溯信息，替代单个功能的trace-link.md）
├ scripts/             # 项目全局可执行脚本（自动化校验、测试脚本，所有功能共用，无需每个功能单独存放）
├ resources/           # 项目全局资源（模板、历史错误案例、规范示例，所有功能共享）
└ features/            # 所有独立功能的存放目录（单个功能目录在此之下，轻量化设计）
   └ [功能唯一标识]/   # 单个功能目录（例如：features/user-register/，独立闭环）
      ├ feature-meta.md     # 单个功能核心元信息（唯一标识、描述、适用范围）
      ├ requirement-design.md # 合并：需求提案+技术设计（精简冗余，避免重复编写）
      ├ task-checklist.md   # 合并：任务计划+验收校验（简化流程，AI完成后自检）
      └ specs/             # 单个功能规范图表（核心保留，AI编码的唯一依据）
         ├ 01-usecase.md    # 用例图（Mermaid语法，可视化场景）
         ├ 02-activity.md   # 业务活动图（覆盖主流程、分支、异常场景）
         ├ 03-component.md  # 组件图（明确模块边界与依赖）
         ├ 04-pert.md       # PERT任务依赖图（关键路径识别，任务拆分合理）
         ├ 05-sequence.md   # 接口时序图（与接口定义一致）
         ├ 06-er.md         # 数据库ER图（满足第三范式，索引合理）
         ├ 07-state-machine.md # 状态机图（无歧义状态流转）
         ├ 08-business-rules.md # 业务规则表/决策树（表格化，无模糊描述）
         └ 09-gherkin.md    # Gherkin场景规范（可映射到测试用例）

【补充说明】
1.  全局共享文件（docs/、scripts/、resources/）统一放在项目根目录，所有功能共用，杜绝冗余；
2.  单个功能目录仅保留4个核心文件，无细碎文件，兼顾简洁性与Skill级严谨性；
3.  所有目录、文件名与上下文（新式PRD）完全匹配，AI可直接解析执行；
4.  明确层级：项目根目录（全局）→ features目录（所有功能）→ 单个功能目录（局部），位置清晰。
```

## 3. 全流程阶段详解（AI 强制执行顺序）

AI 必须严格按照以下顺序执行，**禁止跳过任何阶段，禁止逆序执行**，每个阶段完成后必须等待人工确认，才能进入下一阶段。

### 3.1 阶段 0：初始化与约束加载

**目标**：让 AI 先加载全局约束，再加载功能局部约束，确保从一开始就不跑偏

- **AI 操作**：

    1. 优先加载全局约束：`docs/project.constraint.yaml`、`docs/base.checklist.md`，牢记项目统一规则

    2. 再加载当前功能的约束：`feature.md`元信息、功能的局部约束，确认任务匹配

    3. 检查全局`assets/`中的历史错误案例，避免重复踩坑

- **约束**：禁止在未加载完所有全局 + 局部约束前，开始任何设计 / 编码工作

### 3.2 阶段 1：调研 → 可视化场景确认

**产出**：用例图、业务活动图

- **AI 约束**：

    - 必须覆盖所有主流程、分支、异常场景，禁止遗漏边界情况

    - 所有场景必须明确标注 “做 / 不做”，避免 AI 臆造需求

- **验证门禁**：人工确认场景无遗漏，所有需求被覆盖

- **追溯点**：每个用例生成唯一 ID，记录到`trace.md`

### 3.3 阶段 2：架构设计 → 系统蓝图锁定

**产出**：组件图、部署图、技术依赖图

- **AI 约束**：

    - 必须严格遵循`config.yaml`中的技术栈，禁止擅自引入新的依赖 / 框架

    - 组件职责必须清晰，禁止跨层调用

- **验证门禁**：技术评审通过，架构符合项目标准

- **追溯点**：每个组件生成唯一 ID，关联到对应的用例 ID

### 3.4 阶段 3：任务分解 → 关键路径确认

**产出**：PERT 图、任务清单`plan.md`

- **AI 约束**：

    - 每个任务粒度必须控制在 1-2 天，禁止超大任务

    - 依赖关系必须清晰，禁止循环依赖

    - 必须识别出关键路径，标注优先级

- **验证门禁**：人工确认任务拆分合理，依赖无问题

- **追溯点**：每个任务生成唯一 ID，关联到对应的组件 / 用例 ID

### 3.5 阶段 4：模块设计 → 接口与数据锁定

**产出**：模块职责表、接口时序图、ER 图

- **AI 约束**：

    - 接口必须与时序图完全一致，每个箭头对应一次调用

    - 数据库设计必须满足第三范式，索引设计合理

    - 禁止修改已确认的 ER 图字段，除非走变更流程

- **验证门禁**：接口一致性检查通过，数据模型符合需求

- **追溯点**：每个接口、每个表字段生成唯一 ID，关联到任务 ID

### 3.6 阶段 5：规范定义 → 可执行规则锁定

**产出**：状态机图、规则表、Gherkin 场景

- **AI 约束**：

    - 状态流转必须无歧义，禁止出现未定义的状态跳转

    - 业务规则必须表格化，禁止模糊的自然语言描述

    - 每个 Gherkin 场景必须能映射到时序图 / 数据操作

- **验证门禁**：规范可执行性验证通过，无歧义

- **追溯点**：每个规则、每个场景生成唯一 ID，关联到接口 / 字段 ID

### 3.7 阶段 6：测试设计 → 覆盖度验证

**产出**：测试用例矩阵、规范 - 测试映射图

- **AI 约束**：

    - 所有 Gherkin 场景必须有对应的测试用例，禁止遗漏

    - 测试类型必须覆盖单元、规范、端到端

- **验证门禁**：覆盖率审查通过，100% 场景有测试覆盖

- **追溯点**：每个测试用例生成唯一 ID，关联到对应的场景 ID

### 3.8 阶段 7：小逻辑实现 → 逻辑先行编码

**产出**：流程图、类图、代码、单元测试

- **AI 约束**：

    - 必须先输出函数内部流程图，确认逻辑通顺后再写代码

    - 必须先输出类图，确认结构后再写代码

    - 代码必须严格遵循流程图 / 类图，禁止擅自修改逻辑

    - 必须同步编写单元测试，所有测试通过后才能提交

- **验证门禁**：单元测试 + 规范测试全部通过

- **追溯点**：每个函数、每个代码提交生成唯一 ID，关联到任务 ID、测试用例 ID

### 3.9 阶段 8：大逻辑集成 → 端到端验证

**产出**：端到端流程图、冒烟测试路径

- **AI 约束**：

    - 必须串联所有模块，验证完整业务流程

    - 必须执行冒烟测试，验证核心路径可用

- **验证门禁**：业务场景测试全部通过

- **追溯点**：集成提交 ID 关联到所有模块的代码 ID

### 3.10 阶段 9：用户验收 → 操作引导

**产出**：用户操作流程图

- **AI 约束**：

    - 操作步骤必须清晰，引导用户手动验证

- **验证门禁**：用户确认功能符合预期

- **追溯点**：验收记录关联到所有产出物，完成归档

### 错误溯源操作流程（当线上 / 测试出现 Bug 时）

1. **复现**：还原 Bug 触发路径，记录操作步骤

2. **锁定**：找到出错的代码 / 测试，获取对应的`CODE-XXX`/`TEST-XXX` ID

3. **追溯**：通过`trace.md`向上追溯，找到对应的父 ID：

    - 如果是代码逻辑错：追溯到对应的流程图 / 规则，看是规则定义错了还是代码实现错了

    - 如果是需求错：追溯到对应的用例 / 活动图，看是需求理解错了还是场景遗漏了

    - 如果是流程跳步：追溯是否有阶段被跳过，是否 AI 逆序执行了

4. **修复**：修复问题后，更新对应的产出物，同时更新追溯链

## 5. AI 强约束清单（必须 100% 遵守，无例外）

### 5.1 流程约束

- ✅ **禁止**跳过任何开发阶段，必须严格按照 9 个阶段顺序执行

- ✅ **禁止**在未完成上一阶段人工确认前，进入下一阶段

- ✅ **禁止**修改已经人工确认过的规范 / 图表，除非走正式的变更流程

- ✅ **禁止**在没有生成对应图表 / 规范前，直接生成代码

### 5.2 技术约束

- ✅ **禁止**擅自引入`config.yaml`中未列出的依赖库 / 框架

- ✅ **禁止**修改项目的基础架构、目录结构，除非有明确授权

- ✅ **禁止**跨层调用，必须遵循模块职责定义

- ✅ **禁止**在代码中硬编码敏感信息，必须使用配置文件

### 5.3 行为约束

- ✅ **禁止**臆造需求、臆造规则，所有实现必须严格匹配 PRD 中的规范

- ✅ **禁止**删除、修改历史的追溯记录，所有变更必须留痕

- ✅ **禁止**忽略校验清单中的检查项，完成任务后必须先自检

- ✅ **禁止**生成没有测试用例的代码，所有代码必须有对应的单元测试

## 6. 错误诊断与闭环迭代（Skill 持续优化）

当出现错误时，禁止仅修复代码就结束，必须按照以下流程优化 PRD/Skill，避免重复犯错：

1. **复盘根因**：通过追溯链找到错误的根本原因，是约束缺失？还是规范模糊？

2. **更新约束**：将新的约束加入到`config.yaml`或`checklist.md`中

3. **补充案例**：将错误案例加入到`resources/error_cases.md`中，提醒后续 AI

4. **迭代 Skill**：如果是通用错误，将约束同步到基础 Skill 模板中，让所有功能受益
