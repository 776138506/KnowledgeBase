# [文档类型] 风格指南

> Generator 模式风格指南模板

## 1. 语气和用词

### 1.1 整体语气

- **专业性**: 使用专业术语，但避免过度行话
- **清晰度**: 语言简洁明了，避免冗长句子
- **客观性**: 保持客观中立的语气
- **一致性**: 全文语气保持一致

### 1.2 用词规范

**推荐用词**:
- ✅ "建议"、"推荐"、"考虑"
- ✅ "必须"、"应该"、"可以"（按强制程度使用）
- ✅ 主动语态优先

**避免用词**:
- ❌ "可能"、"也许"、"大概"（除非确实不确定）
- ❌ 被动语态过度使用
- ❌ 模糊的形容词（"很好"、"很快"）

### 1.3 人称使用

- 使用"您"称呼读者
- 避免使用"我"、"我们"
- 使用"用户"、"开发者"等具体角色

## 2. 格式规范

### 2.1 标题层级

```markdown
# 主标题（文档标题）

## 一级节（主要章节）

### 二级节（子章节）

#### 三级节（详细内容）
```

**规则**:
- 主标题只有一个，使用 `#`
- 一级节使用 `##`
- 二级节使用 `###`
- 避免超过四级标题

### 2.2 段落格式

- 段落之间空一行
- 每段 3-5 句话为宜
- 长段落考虑拆分

### 2.3 列表使用

**无序列表**（用于并列项）:
```markdown
- 项目 1
- 项目 2
- 项目 3
```

**有序列表**（用于步骤或排序）:
```markdown
1. 第一步
2. 第二步
3. 第三步
```

**嵌套列表**:
```markdown
- 主项目
  - 子项目 1
  - 子项目 2
```

### 2.4 强调文本

- *斜体*: 用于术语首次出现
- **粗体**: 用于重点强调
- ***粗斜体***: 极少使用

### 2.5 代码格式

**行内代码**:
```markdown
使用 `function_name()` 调用函数
```

**代码块**:
````markdown
```python
def example():
    return "Hello"
```
````

**规则**:
- 始终指定语言类型
- 代码块前后各空一行
- 长代码添加注释说明

### 2.6 引用格式

**块引用**:
```markdown
> 这是引用的内容
> 可以有多行
```

**用途**:
- 引用官方文档
- 引用用户反馈
- 强调重要信息

### 2.7 表格格式

```markdown
| 列 1 | 列 2 | 列 3 |
|------|------|------|
| 值 1  | 值 2  | 值 3  |
| 值 4  | 值 5  | 值 6  |
```

**规则**:
- 表头与内容之间使用 `|---|` 分隔
- 内容对齐一致
- 复杂表格考虑拆分

### 2.8 链接和图片

**链接**:
```markdown
[链接文本](URL "可选标题")
```

**图片**:
```markdown
![替代文本](图片 URL "可选标题")
```

**规则**:
- 链接文本描述清晰
- 图片添加替代文本
- 避免使用"点击这里"

## 3. 内容要求

### 3.1 结构完整

每个文档应包含：

- **标题**: 清晰描述文档主题
- **概述**: 简要介绍背景和目的
- **主体**: 详细内容，逻辑清晰
- **总结**: 关键要点回顾
- **参考**: 相关资源链接

### 3.2 逻辑连贯

- 章节之间有清晰的逻辑关系
- 使用过渡句连接段落
- 避免跳跃性思维

### 3.3 示例丰富

**好示例的特点**:
- 贴近实际场景
- 代码可运行
- 包含注释说明
- 展示最佳实践

**示例格式**:
```markdown
### 示例：[场景描述]

**场景**: [说明使用场景]

**代码**:
```python
# 示例代码
```

**说明**: [关键点说明]
```

### 3.4 图表辅助

**何时使用图表**:
- 展示流程或关系
- 对比数据
- 解释复杂概念

**图表要求**:
- 清晰的标题
- 适当的标注
- 配色协调

## 4. 质量标准

### 4.1 准确性检查

- [ ] 所有信息准确无误
- [ ] 代码示例可运行
- [ ] 链接有效
- [ ] 数据引用正确

### 4.2 完整性检查

- [ ] 所有必要章节完整
- [ ] 关键信息无遗漏
- [ ] 示例覆盖主要场景
- [ ] 参考资料充分

### 4.3 一致性检查

- [ ] 术语使用一致
- [ ] 格式风格统一
- [ ] 标题层级合理
- [ ] 列表格式一致

### 4.4 可读性检查

- [ ] 句子简洁明了
- [ ] 段落长度适中
- [ ] 逻辑清晰连贯
- [ ] 排版美观

### 4.5 技术审查

- [ ] 技术细节准确
- [ ] 遵循最佳实践
- [ ] 考虑边界情况
- [ ] 安全建议适当

## 5. 文档类型特定规范

### 5.1 技术报告

**结构要求**:
- 执行摘要（300 字以内）
- 背景和目标
- 方法和过程
- 结果和发现
- 结论和建议

**语气**: 客观、数据驱动

### 5.2 用户手册

**结构要求**:
- 快速开始指南
- 详细功能说明
- 常见问题解答
- 故障排除

**语气**: 友好、指导性强

### 5.3 API 文档

**结构要求**:
- 概述和认证
- 端点列表
- 请求/响应示例
- 错误代码说明

**语气**: 精确、技术性强

### 5.4 会议纪要

**结构要求**:
- 会议信息（时间、地点、参会人）
- 议程回顾
- 讨论要点
- 决议事项
- 待办事项（含负责人和截止日期）

**语气**: 简洁、行动导向

### 5.5 项目计划

**结构要求**:
- 项目概述
- 目标和范围
- 里程碑和时间表
- 资源需求
- 风险评估

**语气**: 明确、可执行

## 6. 常见错误

### 6.1 格式错误

- ❌ 标题层级跳跃（从 ## 直接到 ####）
- ❌ 列表格式混用
- ❌ 代码块缺少语言标识
- ❌ 表格对齐混乱

### 6.2 内容错误

- ❌ 信息不完整
- ❌ 逻辑跳跃
- ❌ 缺少示例
- ❌ 术语不一致

### 6.3 语气错误

- ❌ 过于随意
- ❌ 过度使用行话
- ❌ 语气不一致
- ❌ 缺乏客观性

## 7. 审查流程

### 7.1 自审清单

在提交文档前，完成以下检查：

- [ ] 通读全文，检查流畅性
- [ ] 检查所有链接
- [ ] 运行所有代码示例
- [ ] 验证数据和引用
- [ ] 检查格式一致性

### 7.2 同行评审

邀请同事审查：

- 技术准确性
- 内容完整性
- 可读性
- 实用性

### 7.3 版本控制

- 使用语义化版本号
- 记录变更日志
- 保留历史版本
